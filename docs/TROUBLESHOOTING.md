# Troubleshooting Guide

What to do when a command, an install, or a debate fails. Install and update steps are in [INSTALL.md](INSTALL.md); the commands themselves in [COMMANDS.md](COMMANDS.md).

## Every install

- **"Unknown command: /tk:explore" right after installing or updating the plugin** - Run `/reload-plugins` or restart Claude Code. The same fix applies when a dispatch says an agent type such as `tk:review-code-finder` is not found: a plugin's agents register when the session loads them.
- **`/tk:ask-gpt` says the key was not found** - The message lists the three places it looked, in order: the environment, the project's `.env.local` (from the folder the command runs in up to the git root), and `~/.claude/plugins/.env.local`. Check that the key sits in one of them, that its line is spelled exactly (`OPENAI_API_KEY=...`), and that its value is not blank. A worktree is its own git root, so it needs its own copy of the project file (`/tk:worktree` makes one). See [API-KEYS.md](../API-KEYS.md).
- **A "Toolkit version notice" at the start of a session** - See [Version notices](INSTALL.md#version-notices) under Update an Existing Project.
- **`/tk:setup` stopped with exit code 3** - It found something that needs your decision (a dirty git tree, a migration in a folder that is not a git repository, locally modified toolkit files, a copy-install of unknown provenance, or a settings file it cannot read, such as one with a trailing comma) and touched nothing. Read its list; rerun with `--force` only after you have decided. `--force` never replaces a settings file it cannot read: it leaves that file exactly as it is and sets up everything else.
- **A toolkit command stops to ask before one of its own steps, in default permission mode** - A plugin command's permission for its own scripts lasts only until you send your next message, and a stage the loop starts for you ("go" into `/execute`, then `/review` and `/document`) gets none of its own. From 7.3.1, `/tk:setup` adds permission rows for the plugin's scripts that cover both, so a prompt there means your project was set up before 7.3.1: run `/tk:setup` again, or `/tk:upgrade`, which reports the missing rows. From 8.0.4, `/tk:review` saves its scope file without a redirect, and the host check's fallback for a project whose remote is neither GitHub nor GitLab (`command -v gh`, `command -v glab`) has two rows of its own, so a prompt on that check means the project was set up before 8.0.4: the same two commands add them. Approve the prompt when it comes.
- **A push was blocked, or Claude Code asked you to approve one** - The push guard checks every push Claude makes before it runs. A block means the push was not in a standard form (`git push -u <remote> HEAD:<branch>`, or `git push <remote> <tag>` for a tag on the checked-out commit, alone in its command or right after the pre-push check), could not be checked, or was flagged by the pre-push check; nothing has left your machine. For the first two, Claude reads the reason and pushes again in a standard form. A flagged push Claude cannot send at all: Claude shows you the report and the exact command, and if you still want it out, type the push yourself with `!` at the prompt, which the guard never sees. Your repository's own pre-push hook, if it has one, still runs on that push, and in the toolkit's own repository it blocks the same hit until you add `--no-verify`. An approval prompt means the push uses `--no-verify` or force, or the check cannot scan it (a delete, `--mirror`, `--tags`). Answer No unless you meant it: your Yes is the "push anyway", and a single key press can answer the prompt, so read it before you press anything. When your repository's own pre-push hook stops a push the guard passed, Claude's retry with `--no-verify` asks you first and names the hook it skips. In bypassPermissions or dontAsk mode, where no prompt is sure to show, a push that would ask is blocked instead. If the guard misbehaves, start a session with `claude --settings '{"disableAllHooks": true}'`, which turns every hook off for that session, and where the guard runs from your own `.claude/settings.json`, as in the toolkit's own repository, remove its `PreToolUse` block there.
- **A review finding lands in "Audited out" as RECEIPT FAILED with a "refused:" reason, or an `/tk:execute` step goes red with `error` verdicts** - The checks runner (`.claude/scripts/run-checks.js`) runs only read-only commands from your project root and refuses the rest before anything runs: command substitution, redirects, subshells, writing flags such as `sed -i`, and any path outside the project. The reason is the one line it prints on stderr and the `detail` field of its JSON. For a review finding, the refusal means the finder's receipt could not be run as written, so the finding is dropped; nothing for you to do. For an entry in your `checks.json`, rewrite the check as a read-only command (`grep`, `test`, your test runner) and keep your test command in the file, since the file replaces the default test run. For a check line in a plan, `/tk:execute` fixes the line itself and runs it again.
- **`/tk:upgrade` stops with "these receipts are each finding's own check, not call-backs", or a receipt's output starts `upgrade-audit: not run:` or `upgrade-audit: unknown argument --receipt`** - The audit's receipts call the audit back through the plugin's stable link, `~/.claude/plugins/data/tk-llm-peer-review/current`, and that link leads to another release than the one running the upgrade. The link moves when a session starts, so this happens after an update taken in the same session, or when a session on another release started while the upgrade ran. Start a new session and run `/tk:upgrade` again; nothing was recorded. If it stops the same way in a fresh session, the plugin's session hook could not make the link: open an issue with the line it printed.
- **`/tk:upgrade` will not finish: "not stamping: the adoption rows ... do not cover this range"** - From v8.0.6 the upgrade records the new version only after every release-note entry since your recorded version has a row saying what it decided (`no action: <why>` or `raised: <what> Decision: <choice>`). The lines above that message name each problem: an entry with no row, a row naming an entry outside the range, a repeated row, or a raised row with no decision. Nothing was written, so let the upgrade add the missing rows and stamp again. A project with no recorded version, or one from before 6.0.0, reads every entry from v6.0.0 once, which is several hundred rows by design.
- **`/tk:execute` reports failing tests in a project with no tests** - npm's stock placeholder script (`"test": "echo ... && exit 1"`) exits 1; the step treats that one as no tests. If the step still goes red, the project has a real `test` script that fails, and the failing lines are in the saved file the step names.
- **A stage says its chain check failed, or refused its input (`bad_shape`, `not_found`)** - From #272 each handoff (`/tk:explore` to `/tk:create-plan`, `/tk:execute` to `/tk:review`, `/tk:review` to `/tk:document`) is decided by `session-init.js --chain <stage>`, which reads a file on disk: the exploration's summary under `reports/explore/`, the newest plan with its saved checks, or the review report's Digest and ledger. A fail names the condition (an open question, a Reaches item missing or answered with a bare `none`, a plan under 100% or a step its checks did not prove, a file the plan committed modified again, a PAGED or NOT FIXED digest line) and the stage stops there: answer the question or the Reaches item, or finish the step, then type the next command yourself (`/tk:create-plan`, `/tk:review <start>..HEAD`, `/tk:document`). A refusal means the file is missing or not in the shape M14 gives (`hitl-stages.md`): a summary without its Open questions or Reaches section, a plan without a progress line, a report without a `## Digest` section, or a Digest line without its plain-words clause after the verdict or with a file name, hash, flag, function name or backticked term in it. A line that passes looks like `- R5: NOT FIXED - a crash when a plan has no start commit, which would ship a hand-off that cannot read its own plan; needs your call - two attempts, reverted to 4cbc9fc`: the words you read come first, right after the verdict's ` - `, and anything technical goes after the next ` - `, in the receipt. That example clears the shape refusal; its not-fixed verdict still stops the chain until the finding is settled, as the list above says. Fix the file or run the stage again; a refusal is never a pass.
- **`/tk:execute` says a step's target check passed before the work** - Each step's target is meant to fail first, for the reason the plan stated, and this one passed instead. A check that passed before the work would pass whether or not the work is done, so it proves nothing. The runner also catches a target whose result before the work already meets what the plan expects after it, and says so in the target's detail: "it already meets its after expect". `/tk:execute` fixes the check or its stated reason in the plan, never the work, records the change in the plan's Outcomes, and runs the before check again; each fix counts against the step's 3 attempts. When no honest check can fail first, the attempts run out and the step stops and asks you, which usually means the plan misjudged where things stood. The kinds of check and their stated failures are in [Kinds of check](COMMANDS.md#kinds-of-check).
- **A check was flagged slow or flaky** - Flaky means it failed, then passed when run again; slow means it took more than half its time limit. A flaky check still counts as a fail. When it is the step's own new check, `/tk:execute` fixes it within the step's 3 attempts, because a check that passes only sometimes proves nothing. An older check that flakes, a guard that was already failing before the step's work, or a slow check that passed does not stop the build: it becomes a `[check]` line under the plan's `## Must-check for review`, naming the saved record that shows the flag, and `/tk:review` checks it. A check that ran out of time is a plain fail, not only slow. Slow is a finding to fix, not a reason to raise the time limit or retry.
- **`/tk:execute` or `/tk:merge` skipped the test run** - The note says "skipped: nothing changed since the passing run at <time> (<commit>)": every tracked and new file is the same as when the suite last passed, so running it again could only show a flaky test. The skip cannot see ignored files (installed packages, `.env.local`) or git tags and branches. When one of those changed and your tests read it, add `--no-skip` to the runner call to force the run. The history behind the skip is `reports/checks/history.jsonl` in the main copy; deleting it starts the usual time over.
- **The cycle page has no "Where the time went" section** - `/tk:document` leaves it out, with one line saying why, when the repo has opted out of the correction ledger (`.claude/.no-correction-log`), when it found no `/tk:explore` or `/tk:create-plan` in the session logs, or when either script failed. Run `node .claude/scripts/correction-ledger.js --cycle-time` to see what it found; `--since <time>` sets the start by hand.
- **The cycle's time leaves out work done in another worktree** - Each working copy times its own cycle. A worktree whose own `/tk:explore` or `/tk:create-plan` cycle was still open when this one began, or began inside it, is a parallel cycle, so its sessions are left out on purpose. A worktree with no cycle of its own, or one whose earlier cycle was documented before this cycle began, is counted as carrying this one on. To time a stretch by hand, run `node .claude/scripts/correction-ledger.js --cycle-time --since <time>` from the copy you want.
- **A worktree's plans and reports are gone after Claude Code closed its session** - Claude Code deletes a worktree it made when the session ends with nothing uncommitted, and the gitignored plans, reports and receipts go with the folder, without a toolkit step running. `/tk:document` copies them into your main folder at the end of every run in a worktree, so look there first: `reports/landing/<branch>.brought-home.json` lists every file it brought home. A session that ended before `/tk:document` ran never copied anything, and git cannot bring those files back.
- **A branch's cycle page never joined the main one** - `/tk:merge` folds a landed branch's cycle page into your default branch's page. A branch merged on the host with its merge button, without `/tk:merge`, is never folded: its cycles and the doc mismatches it found stay on its own page. To fold it by hand, run `node ~/.claude/plugins/data/tk-llm-peer-review/current/scripts/render-html.js --fold-cycle --branch <branch>` from your main folder; folding the same branch twice adds nothing.
- **A plan written before steps carried their own checks has no check lines** - It runs the way it was written: after every step, the project's full test step decides green, and `/tk:review` has no check records to read for it. Nothing needs fixing. To give the remaining work per-step checks, plan it again with `/tk:create-plan` rather than adding lines to a few steps by hand: once a plan has any check lines, every step in it is expected to carry its own, and a step without them becomes a review finding. The line shapes are under [Kinds of check](COMMANDS.md#kinds-of-check).
- **`/ask-gpt` or `/ask-gemini` prints a "deprecated model" warning** - The debate replaces an outdated `GPT_MODEL` or `GEMINI_MODEL` value with the current default and says so. Edit `.env.local` to remove or update the stale value if you want to silence the warning. See [API-KEYS.md](../API-KEYS.md#changing-the-model).

## Copy-install only (Cursor, Codex, other editors)

These come from the setup scripts and the files they copy into a project; a plugin install never meets them.

- **Commands don't show up in Cursor** - Make sure `.claude/commands/` exists in your project root with `.md` files inside. The editor workspace root must be the folder that contains `.claude/`.
- **`/ask-gpt` or `/ask-gemini` fails** - Check that `npm install --prefix .claude/scripts` was run and `.env.local` has valid API keys.
- **"setup.sh: command not found"** - Run the full command from the setup instructions, not just `setup.sh` on its own.
- **"target directory does not exist"** - Create the project folder first: `mkdir -p /path/to/project`
- **Script errors with `/bin/bash^M` or "bad interpreter"** - Line-ending issue. Your shell scripts have Windows-style line endings (CRLF) instead of Unix-style (LF). Easiest fix: delete the folder and clone fresh. Advanced fix: run `git add --renormalize . && git checkout -- .` in the repo.
- **Setup stops with "locally modified file(s) will be overwritten"** - You edited a toolkit-managed file, and setup will not silently replace it. Re-run with `--force` (bash) / `-Force` (PowerShell) added after the target path to proceed - your version is backed up to `.toolkit-backup-<timestamp>/` and listed at the end of the run so re-applying your changes is a checklist.
- **I customized a toolkit file and upgraded - where did it go?** - The setup script preserves your original at `.toolkit-backup-<timestamp>/` at the project root before overwriting. Copy it back if you want to keep your version. Safe to delete the backup directory when done.
- **Setup one-liner fails partway through** - Safe to rerun the command. Leftover `/tmp/tmp.*` folders are harmless and can be deleted. `.toolkit-backup-*/` directories from prior runs are also safe to delete once you have confirmed you do not need the originals.
- **Commands seem outdated or missing sections** - Delete any toolkit command files from `~/.claude/commands/`. Global copies override project commands and cause stale behavior. The setup script warns about this automatically.
