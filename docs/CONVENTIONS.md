# Toolkit Conventions

The conventions live in one file, [`.claude/skills/shared/conventions.md`](../.claude/skills/shared/conventions.md), which ships inside the plugin as `skills/shared/conventions.md`. This page exists so the link is discoverable from the docs folder; it holds no second copy.

A convention is one rule about how your own files should refer to the toolkit, for example "dispatch the review finder for the kind by its scoped name" or "do not keep permission rows for scripts the plugin removed". Each one records the release that introduced it, a check that finds a file still following the old way, and what the fix looks like.

After you update the plugin, run `/tk:upgrade` in the project. It checks your commands, skills, agents, and rules under `.claude/`, plus `CLAUDE.md`, against every convention added since the version the project was last checked against. It also checks `.claude/settings.local.json`, the root files setup seeded (`.gitignore`, `.gitattributes`, `artifacts/README.md`), and the migration record a copy-install move left behind. Eight checks run on every upgrade whatever version you came from, because what they check can drift at any time:

- **C-7, the rules file:** any release can change the seeded rules text.
- **C-9, C-10 and C-11, the repair checks:** permission rows, seeded lines and `tk:` names.
- **C-12 (added in v7.4.0):** reads the rows of your own review kinds in `.claude/toolkit/review-kinds.md`, when the project has that file, and reports a row `/tk:review` could not dispatch.
- **C-14 (added in v7.5.1):** reads your own agents and every line of your own commands, skills and agents that dispatches a toolkit helper, and reports a finder, judge or review-kind agent with no `model:` line, a call to a toolkit finder or the map helper that passes no model, and a call that names a model for a toolkit judge.
- **C-15 (added in v7.6.0):** reads the files setup seeded (`CLAUDE.md`, `LESSONS.md`, `DESIGN-PROFILE.md`, `.claude/toolkit/README.md`) and reports a block that is still an older seed's text, with the current seed's text as the fix, plus a `${CLAUDE_PLUGIN_ROOT}` in a file of yours, where it resolves to nothing.
- **C-16 (added in v7.6.0):** reads `LESSONS.md` and reports an index bullet beyond one sentence while `LESSONS-detail.md` is absent, and a lesson the copy-install's installer inherited from the toolkit's own log. C-15 and C-16 edit files of yours, so each of their fixes is applied only after you approve it on the batch page.
- **C-17 (added in v7.7.0, suggest):** reads your own commands and skills and reports a list line that opens with verify, check, confirm, ensure or make sure (a bold label such as `**Verify:**` allowed first) and carries no command, so the step leaves the model to reason its way to a verdict a command could give (rule M16). The fix is to name the command and its pass signal on that line, or to move the check into `.claude/toolkit/checks.json`. It is a suggestion and is never auto-fixed: a pattern over prose will hit some ordinary sentences, and a judgment step that happens to open with "check" is right to stay as it is.

One more check runs once per project, on the upgrade that brings it: C-13 (added in v7.5.0), Claude Code's built-in prompt audit of your own `CLAUDE.md` and `.claude/` files for instructions newer models no longer need. Plugin files are left out, and a finding on the toolkit part of your rules file goes to the digest as toolkit text you can report to the toolkit.

Each file still behind one becomes a review finding with the check's output attached. Those findings are double-checked by a second agent, fixed automatically, and checked again with the same test, and the run stops to ask you once before it edits any prompt file. A finding about `defaultMode` in your settings is a question for you, asked in that same stop and never fixed automatically. Toolkit files themselves are never touched, because they live in the plugin. Moving a copy-install to the plugin runs the same audit over every convention since the version you came from.

A finding that double-check rejects is remembered in that working copy (in a small record inside the git directory, never committed), so it is not raised again on the next upgrade while the line it is about is unchanged (a finding about a whole file, such as missing permission rows, is never remembered and comes back); the audit's summary says how many it skipped. A fix you declined is not a rejection, so it does come back, as the conventions that edit your own files promise.

The CHANGELOG's Upgrading section names the conventions each release adds, by id.
