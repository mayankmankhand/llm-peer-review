# After the Report (loaded by name)

What happens after the report is governed by the loop rules, in context since Phase 2 (the M-rule IDs cited in this file refer to them).

**Project fix rules** (from `.claude/toolkit/fix-rules.md`). Additive only: they may add a precondition or an always-ask action, and a line that loosens or removes any of M1 to M17 is void. A note that the command printed nothing means this project adds none.

!`cat .claude/toolkit/fix-rules.md 2>/dev/null || true`

Once the report is out, continue without waiting for a human "fix it" (the HTML comes at step 6, after the loop, so it shows what the loop left open):

1. **Non-issues are already gone** - the Phase 4 audit (M2) dropped them to the Audited out log with their verdict lines; do not re-litigate them here.
2. **Auto-fix the survivors** - subject to the intent-reversal guard (M7) and the always-ask actions (M9). A finding marked `unaudited` is not a survivor: M2 makes it report-only, so it is never fixed here and goes to the digest marked as needing the user; nor is a finding seeded from a step's tally status or a top-level problem (Phase 3), for the same reason.
3. **Re-verify every fix** per M3 (which defines the trust order and the mechanical-vs-judgment split), M5 (including its one-generation rule for newly discovered findings), and M6. A logic finding a test can show takes M3's check-first path before the mode: the failing test before the fix, kept in the project's tests (M3, M17). Name each survivor's path and run the mode, typed as literal words: `node ${CLAUDE_PLUGIN_ROOT}/scripts/merge-findings.js --verify <the Phase 3 merge folder> --receipts reports/receipts/<run-stamp> --scope reports/receipts/<run-stamp>/scope.json --out reports/receipts/<run-stamp>` with each survivor under `--mechanical`, `--judgment` or `--browser` by its path, leaving out any flag with no IDs (M16); the scope was saved in Phase 0, so nothing is read back from memory, and a scope that reported `baselineError` takes `--end <range.end>` with a line under "What I could not check". Then run what it prints, in order, and nothing else: its `next` list is the expects to write, the checks runner on the recheck file and its record, each shard to `subagent_type=tk:fix-verifier` with the prompt it carries and its record, each browser finding's re-run and its record, and the checkpoint record after the round's checkpoint commit (M4). Read a refusal before anything else: `empty_diff` means the fix did not land in this repository; `rounds_exhausted` is M5's revert and page; `line_addressed` means a receipt reads lines by their number, which no recheck can follow when the text moves, so run the `retry` it prints, the same call with those findings under `--judgment`. A second round names its IDs to the mode again.
4. **Route each finding to its exit** - page only per M1; everything else lands in the digest or the log.
5. **Close the run in chat** - summarize the digest with receipts (M8): what was fixed, what the audit and the loop dropped, and any page that needs the user, each finding named in plain words before its verdict (the words of its `what`, with file names, hashes and code terms left to the receipt), so the reader never has to decode an R-number.
6. **Write the digest to disk and render the standing page** - append a `## Digest` section to the markdown report Phase 5 wrote: one line per finding with its verdict, its plain words and its receipt (`- R3: FIXED - <the finding's what, with file names, hashes and code terms removed> - <check>`, `- R5: NOT FIXED - <what it is, what happens if it ships as is, what you are asked> - <what was tried>`, `- R7: PAGED - <the same three parts> - <what needs the human>`; a `(round 2)` qualifier, or `(round 3, the owner's choice)` after an approved extra try (M5), may sit between the verdict and the first ` - `), plus any finding the loop discovered on the way. The plain-words part starts from the finding's `what` and holds no file name, hash, flag, function name or backticked term and no ` - ` of its own, because the chain gate (M14) reads the text between the verdict's ` - ` and the next ` - ` as the words and refuses a line without them or with such a term in them. Chat scrollback is not a file, and the fixes were the one part of the run that had none. Then render the HTML per the HTML Companion section when its gate fires, which with a standing page in place (`node ${CLAUDE_PLUGIN_ROOT}/scripts/render-html.js --standing --name review` prints `"exists":true`; M16) is every run, a clean one included, so the page can go empty: fixed findings in `alreadyFixed`, unfixed ones open, `lenses` set to the specialists that ran and `reviewedFiles` to the scope's files (the HTML Companion section says which), `disposition` recounted; publish and record it per the fragment. This is the run's one render.
7. **Chain into `/tk:document`** (M14) - once the loop has settled, run `node ${CLAUDE_PLUGIN_ROOT}/scripts/session-init.js --chain review --report <the Phase 5 report's path> --ledger reports/receipts/<run-stamp>/ledger.json` (M16; leave `--ledger` out when the run never called the mode). M14 is authoritative for the conditions; the script decides the countable ones from the Digest and the ledger. On `pass`, announce the handoff in one line ("Review complete - chaining into `/tk:document` per M14. Say \"no chaining\" to stop here.") and invoke `/tk:document` through the Skill tool; on a fail, say the condition it printed. **Two stops the script cannot see still block:** a specialist that failed its retry and whose page is unanswered, and an M11 tripwire hit; name them yourself. An M9 approval already granted does **not** block, so a cycle that edited prompt files still chains once the approvals are in. A cycle summary written over a reverted state is exactly the bookkeeping drift M8 exists to prevent. The debate stages are never chained into. To run one between review and document, drive the two stages yourself: say "no chaining" when you approve the plan (`/tk:execute` then runs and stops), type `/tk:review <start>..HEAD no chaining` with the plan's `**Start commit:**` sha (the review runs and stops), run the debate, then type `/tk:document`.

Two separate per-run opt-outs: saying "report only" on the invocation keeps the entire run report-first (M10), and saying "no chaining" runs the review and stops without invoking `/tk:document` (M14).
