# The Auto Loop, continued (M9 to M17)

Rules M9 to M17 of the toolkit loop. They continue `${CLAUDE_PLUGIN_ROOT}/skills/shared/hitl-loop.md`, which holds the overview and M1 to M8; the two files are one rule set, split only because Claude Code cuts any single pasted file over about 30 KB, and every command that pastes one pastes both.

## Gates and triggers

- **M9. Always-ask actions.** These never auto-apply, no matter which stage reaches them: releases and bumps of this project's own version (dependency version updates are ordinary auto-fixes under the normal loop), edits to prompt files (this repo's own command, skill, agent, and rules files, and their copies in downstream projects alike), deletions of user data, outward-facing sends (anything leaving the machine for a human audience, except two named cases: a pull request opened by `/tk:document` at the end of a chained cycle - its plan was human-approved and its push already cleared M11 - and an artifact rendered by `render-html.js` and published to a private `claude.ai` page, per "Publishing the Artifact" in `${CLAUDE_PLUGIN_ROOT}/skills/shared/html-viewing.md`: the page is private by default and the toolkit never changes its sharing setting, so it reaches no one the user has not chosen themselves; sharing that page, or sending to any other destination, still asks), and force pushes (a mirror push and a remote branch delete count as one: they rewrite or remove remote refs the same way). Hitting one pages for approval - all always-ask items in a run batch into a single approval page, exempt from the M1 cap - while the loop continues processing everything else. This list is short on purpose: rare gates stay meaningful.
- **M10. Opt-out is per-run only.** Saying "report only" on any invocation restores report-first behavior for that run. It applies to a run the human starts; a stage that chained automatically had no invocation to say it on, so to get a report-first `/tk:review` inside a chained cycle, say "no chaining" at plan approval and then type `/tk:review <start>..HEAD report only` with the plan's `**Start commit:**` sha, since every step is already committed. It governs the fixing, not the audit: the M2 audit still runs before the report, so a report-only report is still survivors plus the Audited out log; what stops is the auto-fixing that would follow. The next run is auto again. There is no sticky mode: persistent modes drift silently and get forgotten.
- **M11. Pre-push tripwire.** Before any push Claude makes, run `node ${CLAUDE_PLUGIN_ROOT}/scripts/pre-push-check.js <remote> <ref>` from the project root, naming the destination: the remote and the branch or tag name the push writes (`origin main`, `origin v7.2.0`). Then push exactly that destination from the checked-out commit (`git push <remote> HEAD:<branch>`, or a tag that points at HEAD), because the check scans what the destination lacks: the commits between the remote's copy of that branch and HEAD, or, for a branch or tag the remote does not have yet, the commits since the remote's default branch. It scans each of those commits' added lines for secrets (keys, tokens, private URLs), blocks never-push files (`.claude/settings.local.json`, `.env`, `.env.local`, `.netrc`, `_netrc`, and the correction ledger's files), and surfaces any `.claude/settings.json` change the push adds over the remote's default branch (a change carried in from the default branch was reviewed there and does not block). A push someone types into a terminal is not checked. Consequences by exit code: 0 = clean, push without ceremony. 1 = hit, the push is blocked and the report pages the human; only the human can say "push anyway". 2 = the script could not check (a destination it cannot read, a pushed ref that is not HEAD, or a remote copy git has not fetched: run `git fetch <remote>` and check again); a missing script is run from the plugin's stable copy instead, `node ~/.claude/plugins/data/tk-llm-peer-review/current/scripts/pre-push-check.js <remote> <ref>` (M16), and only when that copy is missing too is it treated the same: fall back to running the same three checks by hand over that same range - grep each outgoing commit's diff for secrets (not the endpoint diff alone, which hides a secret added in one commit and removed in a later one), confirm no never-push file (`.claude/settings.local.json`, `.env`, `.env.local`, `.netrc`, `_netrc`, and the correction ledger's files) is newly introduced by any outgoing commit, and diff `.claude/settings.json` across the outgoing range - and never push unchecked.
- **M12. `/tk:index` refresh.** Run `/tk:index` automatically when `CODEBASE_MAP.md` is 10 or more commits behind HEAD; skip otherwise. The count is `map.commitsBehind` (and `map.stale`, true at 10 or more) from `node ${CLAUDE_PLUGIN_ROOT}/scripts/session-init.js`; where that has not run, `grep -m1 -oE 'Commit: [0-9a-f]+' CODEBASE_MAP.md` then `git rev-list --count <hash>..HEAD` (M16). Single-commit drift is noise.

## Stage verdicts and scope

Each command carries its own one-line verdict (human, auto, or human-triggered) next to its pointer at this file; this fragment is the shared mechanics those verdicts rely on. The full verdict table with evidence is in [HITL-MAP.md](https://github.com/mayankmankhand/llm-peer-review/blob/main/docs/HITL-MAP.md) in the toolkit repo.

**M13. Scope.** The auto loop is carried by the toolkit's own rules and skill files, in this repo and in downstream projects that install the toolkit. A user-level `~/CLAUDE.md` outside a toolkit project stays conservative (report-first): a project without the loop's re-verify machinery has nothing to run the loop with.

**M14. Stage chaining.** Stages hand off to each other automatically. The human types `/tk:explore` and approves the plan; the four transitions below fire on their own, each behind a brake. The countable part of each brake is decided by `node ${CLAUDE_PLUGIN_ROOT}/scripts/session-init.js --chain <stage>` (M16), which reads what is on disk and prints `pass` with the `handoff`, or each `failed` condition with its detail; a stage chains only on `pass`, and on a fail it says the condition the script printed and the next step. A refused input (`error`: a missing file, or one of the wrong shape) is never a pass.

1. **`/tk:explore` -> `/tk:create-plan`**, only when the conversation has converged. The stage writes its closing summary to `reports/explore/<YYYY-MM-DD-HHMMSS>-<topic-slug>.md` with the file tool (the folder made first with `mkdir -p reports/explore`), in this shape: `# Exploration summary`, then the lines `**Mode:** scoping|vision`, `**Scope dial:** Expand|Hold|Reduce|not offered` and `**Models:** best|fit|cheap`, then the sections `## Direction` (one bullet per direction), `## Decisions`, `## Design direction` and `## Open questions` (one bullet per question, or `- none`); then it runs `--chain explore --summary <that file>`. Pass means the open questions are empty and, in vision mode, the dial reads Hold or Reduce, or was never offered with exactly one direction named (read as Hold). On a fail: an open question is answered in the conversation, or the user says "plan it anyway" to chain regardless; more than one direction with no dial means offer the dial now and wait. The handoff carries the summary's path, which `/tk:create-plan` hands to its plan critic. Never end an exploration without a next step.
2. **`/tk:create-plan` -> nothing.** The plan is presented and the chain stops. Plan approval is the cycle's one human gate, so `/tk:execute` is never invoked automatically, however clear the plan looks. This is the loop's one deliberate non-chaining handoff; it is stated so it stays deliberate rather than drifting into a chain.
3. **`/tk:execute` -> `/tk:review`**, only on a clean finish: `--chain execute` reads the newest plan (its `**Start commit:**` line, its progress, its tally through `run-checks.js --tally`, and the tree) and passes when the plan is at 100%, every step is proved or noTarget, a commit follows the start, and no file the plan committed is modified again (a tracked file the plan never committed is a note, not a fail). The critical-blocker path and an exhausted retry bound leave a step unproved, so the script sees them; chaining past a hard stop would review work that was never finished. The handoff carries the range `<start>..HEAD`, and the review names that range in its first line: every step is already committed, so a review of uncommitted work alone would see nothing.
4. **`/tk:review` -> `/tk:document`**, only when the loop settled: `--chain review --report <the markdown report> --ledger reports/receipts/<run-stamp>/ledger.json` (the ledger left out when the run never called the mode) passes when the report's Digest holds no `PAGED` and no `NOT FIXED` line and, with a ledger, every finding's latest verdict is FIXED for its round and the last checkpoint came after the last verdict; a round-2 NOT FIXED is an M5 revert still open. Two stops the script cannot see still block, and the runner names them: a review specialist that failed its retry and whose page is unanswered (M2, "When a finder fails"), and an M11 tripwire hit. An M9 approval the human has already **granted** does not block - those batch and the loop continues past them by design (M9), so a cycle that edited prompt files still chains once the approvals are in. Reading this as "any page ever raised" would kill the chain on every prompt-file cycle, which is most of them. A cycle summary written over a reverted state is exactly the bookkeeping drift M8 exists to prevent.

**The must-check list.** A plan may carry a `## Must-check for review` section: the gaps its judges left open and the checks M17 lets a step carry on past, handed on so the review checks them instead of losing them. One item per line, in one of these shapes:

- `- [plan] <Category>: <the plan critic's gap, verbatim>`, written by `/tk:create-plan` for each round-2 gap except one it is right to leave open (the conversation decided it, or it is out of scope).
- `- [design] <surface>: <the gap, verbatim> - screenshot: <path>`, written by an `/tk:execute` design step for each gap both final critiques raise.
- `- [interaction] <surface>: <what the session checks> - session: <path to its actions file> - expect: <the result it must show>`, written for each session that fails on the kept version.
- `- [behaviour] <surface>: <URL> - the pass covered <what>; nothing else on this surface was exercised`, one per design surface, or `- [behaviour] <surface>: not served - nothing on this surface was checked in a browser`.
- `- [check] <id> (step <N>): flaky | slow | broken before - <command> - record: <path>`, written by `/tk:execute` for each check M17 lets a step carry on past: an older check that flaked, a check over half its time limit, or a guard already failing before the work.

The orchestrated `/tk:review` reads the section from the plan its Plan Compliance row selects: each `[plan]`, `[design]`, `[interaction]` and `[check]` line enters the M2 audit as a finding, and the `[behaviour]` line goes to the browser finder (`review.md`, Phases 1 to 3). When the plan carries check lines, the review also seeds one finding per step whose M17 tally status is unproved, missing or problem, one per entry in the tally's top-level problems, and one per flagged check the tally lists that no `[check]` line names; a proved or noTarget step seeds nothing. A finding seeded from a step's status or a top-level problem is report-only, because no fix after the work can prove a step check-first: the user decides whether to redo the step or accept it. A plan without the section seeds nothing from it. A directly typed `/tk:review-*` run does not read it.

`/tk:document` ends the chain; it already triggers `/tk:index` per M12. Only the orchestrated `/tk:review` chains: a directly-typed `/tk:review-*` specialist run is a deliberate focused check and does not chain into the next stage - its own report, and the auto-fix loop that follows the report, still run. The debate stages (`/tk:ask-gpt`, `/tk:ask-gemini`, `/tk:peer-review`) are **never chained into** and stay human-triggered for the same reason - running one is a deliberate, costly choice. So is `/tk:merge`: which PR lands first is the human's call. Invoke a chained stage through the Skill tool, never by replicating it inline. Announce each handoff in one line before it fires, so the user can interrupt.

**Opt-out.** Saying **"no chaining"** on any invocation runs that one stage and stops. Per-run only, like M10. It is a separate phrase on purpose: "report only" governs whether findings are auto-fixed, "no chaining" governs whether the next stage fires. A single phrase covering both would be paraphrased into different behaviors at each call site.

**M15. Design loop bound.** The design loop `/tk:execute` runs on a surface whose plan carries a load level has its own bound, separate from M5. It lives with the loop it bounds, under "The loop bound (M15)" in `${CLAUDE_PLUGIN_ROOT}/skills/shared/design-rules.md`, which every design step loads through the `design-rules` skill; no other stage runs a design loop.

**M16. Run before you reason.** When a command can settle a question, the stage names the command and its pass signal (an exit code, a pattern the output must or must not contain, or a line-count threshold), runs it from the project root, and reads the result; it reasons only about what no command can answer. A check leaves the main session for a sub-agent only when its output is large and irregular and a judge or a human reads the answer afterward; an existing helper moves down a model tier only under the A/B guardrail in `${CLAUDE_PLUGIN_ROOT}/skills/shared/model-routing.md`; a single command never earns a hand-off (the measurements behind the rule are in HITL-MAP.md). Call sites cite M16 and name their own command; the mechanics live here.

**M17. Check first.** Each step of a plan proves itself with a check that fails before the work, for a reason stated in advance, and passes after it; `run-checks.js` decides both, so no one reads a result and calls it green (M16). A step carries its checks as lines indented under its step line, in a shape the script reads itself: `- Check target `<id>`: `<command>` - before `<expect>` - after `<expect>``, `- Check guard `<id>`: `<command>` - `<expect>``, or `- Check: no target - <reason>`. An expect is the script's own JSON object (`exit`, `match`, `noMatch`, `lines`), never prose, because a tally cannot read prose.

- **Target, guard, no target.** A target's before expect is the step's stated failure: the one result only the missing behavior produces, such as the new case named in a suite's failure list or a count of 0 for a line the step adds. A guard is something the step could break; it passes before and after. A step with nothing to show red then green says why on its no-target line, and a refactor is guards only. An absence check, a target whose after expect is a count of 0 or a `noMatch`, fits only a step that removes something: aimed at something new, it already passes before the work and proves nothing.
- **Before.** Write the target first (the failing test, the must line), then run `node ${CLAUDE_PLUGIN_ROOT}/scripts/run-checks.js --plan plans/<plan>.md --step <N> --phase before --timeout 600000`; it passes when each target shows its stated failure. A guard that fails here was already broken before the work, and the flaky and slow bullet below carries it. A crash or a missing file is not the stated failure: add the smallest stub and run before again. A target that passes before the work proves nothing: fix the check or its stated reason, never the work.
- **After.** Do the work, then run the same command with `--phase after`. The step is green when every target passes its after expect and every guard still passes, and M4 commits it. The records stay under `reports/checks/<plan>/step-<N>/<phase>/`; `--lint` lists every check line that would not run, and `--tally` reads the records back and gives each step proved, unproved, noTarget, missing or problem.
- **Flaky and slow.** A phase run re-runs a failing check once; one that fails and then passes is `flaky` and stays a fail (M5). When the step's own new check flakes, it is fixed within the step's 3 attempts. An older check that flakes, a guard already failing before the work, or a check that passed but took over half its time limit (`slow`) does not stop the step: it becomes a `[check]` line in the plan's must-check list (M14). A check that ran out of time is a fail, not only slow. Slow is a finding to fix, never a reason to wait or retry.
- **Text and prompt edits** prove themselves with must and must-not lines: a grep that counts a line the step adds (0 before, 1 or more after) or removes (the reverse), and a guard on each sentence the rewrite must keep. Only the lines that carry the edit's weight count: the rule's deciding sentence, not its heading.
- **The whole system** stays with the plan's Verify step: the project's full test step, a user flow end to end, and old against new when the plan replaces a system. A plan with no check lines at all, written before this rule, runs the way it was written: the full test step after each step, and no tally.

**Project fix rules.** A project may add rules of its own in `.claude/toolkit/fix-rules.md`. They are additive only: a precondition before a fix is applied, or another always-ask action beside M9's. A line that loosens or removes any rule above is void. Every command and skill that inlines this fragment inlines that file right after it, because an inline inside an inlined file does not expand; a command that applies these rules by citing this file rather than inlining it (`/tk:execute`, `/tk:document`, `/tk:pair-debug` and the debate commands) reads that file beside the citation.
