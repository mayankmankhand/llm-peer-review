## What I Learned
<!-- Add entries after each session where you learned something new -->

- **XML tags in prompts are a real thing, not just hype.** All three major providers (Anthropic, OpenAI, Google) recommend XML for complex, multi-section prompts. The key insight: XML helps AI distinguish *what kind of content* a section is (rules vs templates vs examples), which markdown headers alone can't do.
- **Hybrid approach beats all-or-nothing.** Don't replace markdown with XML - use both. Markdown headers stay for human readability, XML wraps content blocks for AI parsing. Pattern: header outside the tag, content inside.
- **AI peer review recommendations often over-engineer.** When /ask-gpt and /ask-gemini reviewed the XML plan, they recommended namespaced tags (`tk_rules`), a formal schema file, testing rubrics, and a three-wave rollout. Most of that was unnecessary for 9 small files. Trust your gut when something feels like too much.
- **A worktree is just a folder, a branch is just a pointer.** They're independent. Deleting a worktree folder does not delete the branch, PR, or any commits. You can always re-create a worktree from the same branch. Think of it like closing a document window vs. deleting the file.
- **Worktree detection: `--git-dir` vs `--git-common-dir`.** To check if you're in a Git worktree, compare `git rev-parse --git-dir` with `git rev-parse --git-common-dir`. If they differ, you're in a worktree. The first attempt used `--show-toplevel` vs `--git-common-dir`, which compares a directory path to a `.git` path - they're never equal, so it always said "worktree." The review process caught this before it shipped.

- **Use deterministic scripts for structural data, not LLMs.** When generating a file tree index, the first instinct was to have Claude scan and describe every file. Both GPT and Gemini called this out: "using an LLM to generate a token-saving index burns more tokens than it saves." A 20-line Node script using `git ls-files` does the job in milliseconds with zero token cost. Reserve LLMs for judgment calls, not mechanical tasks.
  - **Update (v4.4.0, issue #97):** The lesson is correct about mid-session LLM scanning, but during v3.4 it was over-applied to cancel ALL LLM involvement in index generation, including the one-time upfront generation that issue #70 originally wanted. The result (v3.4 through v4.3.x) was a flat file tree that did not save tokens at all - a directory listing is essentially free for Claude. v4.4.0 brings back the original vision: one-time upfront generation via parallel subagents (Cartographer-style), amortized over many sessions. Refined rule: **do not have Claude scan files mid-session; do invest tokens once when generating a persistent map the project keeps and rereads.** A ~$1 generation cost pays back across 5-10 sessions via reduced file reads.
- **Version bumps touch more files than you think.** Six files track the toolkit version: VERSION, package.json, package-lock.json, .claude/rules/toolkit.md (stamp comment), CHANGELOG.md, and AGENT-SETUP.md (title + "What's new" block). Easy to miss one - v4.2.1 shipped with package.json, package-lock.json, and toolkit.md stale; v4.1 missed toolkit.md too. **Use `bash scripts/setup/bump-version.sh <ver>`** - it handles the 4 mechanical files and prints a checklist for the 2 prose files. An earlier version of this lesson claimed "no automated fix possible because the checklist would leak to downstream users" - that was wrong. `scripts/setup/` is maintainer-only; setup.sh's propagation allowlist (setup.sh:352-354) only copies the three runtime scripts, so anything else added to `scripts/setup/` stays in the toolkit repo. (Status as of v4.5.0: setup.sh now lives at `scripts/setup/setup.sh` and the propagation block has moved to ~lines 463-465; the allowlist behavior is unchanged.)
- **Never interpolate shell variables into inline `node -e` strings.** If `$TARGET` contains a single quote (e.g., `/home/user/it's-a-project`), it breaks the JS string literal and `2>/dev/null` silently swallows the error. Pass paths via environment variables instead: `TARGET_DIR="$TARGET" node -e "const dir = process.env.TARGET_DIR; ..."`. This avoids all quoting issues.
- **`settings.json` can get modified by research subagents.** During the index format research, a subagent fetching aider.chat added a WebFetch permission and additionalDirectories to `.claude/settings.json`. Always run `git diff` before committing to catch unintended changes from subagent side effects.
- **Permission approvals can land in the wrong settings file.** When Claude Code prompts for a new Bash permission and the user approves it, the entry can get appended to `.claude/settings.json` (shared/committed baseline) instead of `.claude/settings.local.json` (user-specific, where the project convention says real permissions live). Also captures literal argument values, so test-run entries like `Bash(bash scripts/setup/bump-version.sh not-a-version)` end up in the file. Mitigation: `git diff .claude/settings.json` after approving any new permission, and move the entry to `settings.local.json` with a broader glob (`Bash(bash scripts/setup/foo.sh *)`) if the script is meant to be allowed long-term.

- **"Do I understand it?" vs "Can I use it?" is the right split for review skills.** When adding `/review-copy`, the key insight was that clarity/orientation and usability/accessibility are genuinely different concerns. A page can be perfectly usable (good contrast, accessible forms) but still confuse a newcomer who doesn't know what they're looking at. Separate skills with a clear tie-break rule ("meaning/orientation = copy, interaction/accessibility = UX") prevents muddled feedback.
- **Run debates on plans, not just finished work.** Running `/ask-gpt` and `/ask-gemini` on the plan (before building) caught four refinements that would have required rework later: audience assumption wording, severity anchor calibration, auto-detection heuristics, and the need for a non-goals section. Cheaper to fix a plan than to rewrite a shipped skill.
- **Boundary annotations in few-shot examples teach thresholds, not just format.** Adding a meta-note like "this would be skipped if X, is a Suggest because Y" inside an illustrative finding turns a passive template into an active boundary lesson for the model. Applied this in `output-template.md` to teach the Skip-vs-Suggest line via one example with explicit threshold logic, rather than padding the file with 5 borderline examples (issue #98).
- **DRY refactors create duplication-of-the-other-kind bugs.** When `/review`'s hardcoded output format was replaced with `!cat` inlining of the shared template, the shared template's own Summary block ended up rendering on top of the orchestrator's own Summary block - two Summary blocks per report. Standard `/review-*` checks missed it; the `/ask-gemini` debate caught it. Lesson: when DRYing, audit both sides of the new connection for what each independently provides (issue #98). **Recurred in #143 in a sharper form:** the approved scope addition fixed a creation-date sort bug in `gh pr list`, and the GitLab equivalent was pasted in beside it straight from the issue text, carrying the identical defect (`glab mr list --per-page 1` also sorts by creation date, not merge date). The shipped fragment then contradicted its own Notes bullet six lines below, which forbade exactly that pattern. Both `/review` specialists caught it independently. The generalized rule: when you fix a bug in ONE branch of a two-branch construct (two hosts, two platforms, two code paths), grep for the sibling before shipping. The moment you are most blind to a duplicated defect is right after you have fixed it once, because the fix feels done.
- **Issue framing != actual problem.** Issue #98 was titled "/review prompt may force model to manufacture issues" - the user's hypothesis was biased phrasing. `/explore` (vision mode) revealed the real problem: thin explanations + low severity bar, not invented findings. Trust the explore step to reframe even concrete-sounding issues; the original framing is just one hypothesis (issue #98).
- **Diagnostic output to stderr when stdout is captured by another LLM.** When a script's stdout flows into a downstream LLM's context (debate transcripts, multi-step workflows, anything that reads the script's output and puts it in a future prompt), any informational print silently pollutes the downstream prompt. `/review` caught this on the v4.5.0 model-bump safety net (issue #100): the new `Using GPT model: gpt-5.5` line and the deprecation warning were `console.log`, so they would have ended up in `/tmp/ask-gpt-debate.md` that rounds 2 and 3 re-read. Fix: route diagnostic prints to `console.error`; reserve stdout for "the payload another tool expects to parse." Rule of thumb: stdout = data, stderr = chatter.
- **Reasoning models share their token budget between reasoning and output.** `max_completion_tokens` (OpenAI) and `maxOutputTokens` (Gemini) cap the SUM of reasoning/thinking tokens and visible output. A 4096-token cap on a long-context input can be entirely consumed by reasoning, leaving zero tokens for visible output - the API returns `finish_reason: length` with empty content, exit code 0, no error. OpenAI's docs recommend reserving at least 25,000 tokens for reasoning models; Gemini's SDK default is 8,192 (we were below that). v4.6.0's GPT and Gemini scripts default to 32,000 with env overrides (`GPT_MAX_TOKENS`, `GEMINI_MAX_TOKENS`) for users who want lower caps to limit cost. See issue #101.
- **Silent empty bodies need active detection, not just happy-path returns.** Before #101's fix, both scripts had `return typeof text === 'string' ? text.trim() : ''` - any failure mode that produced empty content (token cap hit, refusal, safety block, wrong model) silently returned `''` with exit code 0. Detection means actively inspecting `finish_reason` (OpenAI) / `finishReason` (Gemini), `refusal`, `safetyRatings`, and `usage.completion_tokens_details.reasoning_tokens` / `usageMetadata.thoughtsTokenCount`, then throwing a descriptive error naming the cause AND the fix (e.g., "Raise GPT_MAX_TOKENS or shorten the input"). Token counts in the error are essential - "finishReason: MAX_TOKENS, thoughts_tokens: 92, candidates_tokens: 4" tells the user thinking ate 96% of budget, way more actionable than "empty body."
- **Per-session temp file paths solve concurrent-tab collisions; session-ID recovery needs to handle the multi-tab case.** Hardcoded paths like `/tmp/ask-gpt-debate.md` collide when two Cursor tabs run `/ask-gpt` in the same project. Fix: each slash command invocation generates a session ID (`echo "$(date +%s)-$RANDOM"`) and embeds it in every temp file path. Belt-and-suspenders: (a) write `<!-- Session: <id> -->` as the first line of the debate file so the ID is recoverable from disk if context compression drops it, (b) add `warnIfSessionMismatch` to the Node script that detects mid-flow ID regeneration via filename suffix comparison, (c) recovery instructions in the slash command must warn against blindly picking the most recent file under concurrency - it might belong to a parallel tab. See issue #101.
- **Run /ask-gpt and /ask-gemini in parallel when the change is worth real scrutiny; convergence between independent reviewers is signal.** Running both debates against PR #104 (4-field debate-summary format) surfaced the same template-slicing concern from both sides: GPT flagged that the inlined shared template could leak `/review`-only sections into debate output; Gemini independently flagged that the heading-based slice marker was fragile. Neither reviewer saw the other's transcript - they reached the same fix (machine-readable `BEGIN/END` markers around just the reusable finding contract) from different starting concerns. When two independent debates converge on the same gap, treat it as load-bearing: it almost certainly is. Running one debate gives you a second opinion; running both gives you a triangulation. Doubles the API spend, but worth it for changes you'd hate to re-fix later. Caught while validating the unchecked "end-to-end summary test" item from PR #104's test plan.
- **Cross-platform mirrors can hide pre-existing gaps; audit before assuming a small change stays small.** Mirroring a one-line addition from `setup.sh` to `setup.ps1` for issue #113 (`html-look.md` propagation) surfaced that `setup.ps1` had never copied `.claude/skills/` at all - every SKILL.md and shared reference file was missing on Windows. The "small mirror" expanded into "small mirror + gap fix" once the two scripts were compared side by side. Lesson: before mirroring a change, grep the target script for the prerequisite logic (`grep -i skills setup.ps1` would have caught this instantly). Document the scope expansion in the plan's Outcomes section so reviewers can audit the choice to expand vs defer. Related: two more `setup.ps1` gaps surfaced during the same review (no `VERSION` copy, no `generate-index.js` copy) and were correctly left out of scope as follow-ups - one expansion is fine, two compounds risk.
- **Define a judgement gate once, in countable terms, consistent with its governing rule.** Issue #116's debate-HTML gate shipped described three ways: the rule file said "3+ Recommended Actions," the new shared template added "OR genuine disagreement," and the command heading said "when the debate had substance." `/review` (both the commands and plan specialists, independently) flagged two problems: the template diverged from the single-source-of-truth rule file, and "genuine disagreement" would nearly always fire because debates are *designed* to argue across 3 rounds - making a "judgement" gate effectively default-on. Lesson: a gate should be one objectively-checkable condition (a count, not a vibe), and it must say the same thing everywhere it appears. When the same gate is described in 2+ files, they are now a consistency surface that drifts. Fix was to collapse to the single countable trigger across all three places.
- **A gate must be countable against the output the model actually produces.** Issue #137's debate convergence gate shipped as "end early only if the round 2 reviewer response has an empty Still Discussing section AND no New Observations." `/review` (commands specialist) caught that the debate scripts instruct the reviewer to ALWAYS emit all three headings, so a converged reply reads "## Still Discussing / None - all points resolved." - not an empty section. The gate was countable against an idealized reply, not a real one: one session would treat "None" as empty and stop, another would read it literally and run round 3, paying an extra API round in exactly the debates that converged. Fix: define "settled" once (absent, empty, or only a none-style placeholder with no substantive bullet) and apply the identical definition to both sections. Companion to "Define a judgement gate once, in countable terms": defining once is not enough - test the wording against a sample of what the upstream format actually produces before shipping it.
- **`gh pr list --state merged --limit 1` sorts by CREATION date, not merge date.** It can return a stale PR (an old PR created long ago but merged recently sorts above a newer one). Discovered during #116's `/document` cycle-summary first-run fallback ("window since the last merged PR"): the command returned PR #104 even though #113-#116 shipped later (those went direct to `main`, not via merged PRs). For "most recently merged," sort explicitly: `gh pr list --state merged --json number,mergedAt --jq 'sort_by(.mergedAt)|reverse|.[0]'`, or use `git log --merges`. The D3 fallback in `document.md` still uses the naive `--limit 1` form - worth tightening in a follow-up.
- **HTML output is useless if the user only gets a file link - it opens as source in the editor.** Issue #102's HTML feature generated files in `artifacts/html/` and handed the user a path. In Cursor/VS Code, clicking that path opens the HTML *source code*, not the rendered interactive page, so the user saw markup instead of the dashboard. Fix (R4): after writing any HTML artifact, the command runs the platform opener (`open` on macOS, `wslview`/`explorer.exe` on WSL, `xdg-open` on Linux) so the rendered page opens in a browser, and the opener permissions live in `settings.local.json` so it does not prompt. Rule: if you generate something meant to be *viewed*, open it for the user; do not assume a link behaves the way you expect in their environment.
- **A diff review of already-closed work still earns its keep.** After #113-#116 were implemented and closed across several sessions, running `/review` on the cumulative diff (`<last-release>..HEAD`) surfaced 14 findings, including two real gaps: the `artifacts/` scaffold was never propagated downstream by either setup script (a tracked README that existed upstream but never reached users - same class as the earlier setup.ps1 skills gap), and the browser-open friction above. "Done and closed" is not "reviewed." When a multi-issue feature lands across several sessions, review the combined diff once at the end - cross-cutting gaps (propagation, file-to-file consistency) only show up when you look at all the pieces together, not issue by issue.
- **Don't trust merged review severities without verifying the source lines.** Discovered while triaging the /review report for issue #117. The plan reviewer claimed `/audit-html`'s SKILL.md inlined `html-outputs.md` twice (lines 33 AND 134), framing the second inline as a copy-paste defect. The commands reviewer reviewed only line 33's over-broad inline. In synthesis I merged the two findings into one R1 (Block) and reported it to the user as "two-character fix at line 134." It was a hallucination: line 134 already correctly inlines `html-look.md` (the visual tokens, which is what the HTML Report Judgement section needs). A 30-second `grep -n "^!cat" SKILL.md` would have shown the actual inlines and prevented the false escalation. Rule when merging cross-specialist findings: if two specialists describe the same finding differently (especially when one claims a defect the other did not see), open the file and confirm the line state before keeping the higher severity. Cheap to verify; expensive to send the user chasing a non-bug.
- **Review proposed prompt edits before applying them, and triage the volume hard.** Issue #121 added a conditional test-step heuristic to `/create-plan`. Instead of applying the edits then reviewing, we ran `/review` (review-commands, 4 parallel lenses) against the *proposed* text while the working tree was still clean - a pre-application review. It surfaced 13 findings across all three severities, but only ~3 were real: one true defect (the Verify step depended on a deletable optional setup step, so deleting it dangled), one genuinely valuable for the non-technical owner (no plain-English "why" on auto-added steps), and one cheap on-intent line (a "when in doubt, skip" tiebreaker). The other ~10 were edge cases an intelligent model handles, things already covered by existing wording ("and/or, whichever fits"), or scope-widening into files the issue never named (`execute.md`, map-absent fallbacks). Lesson: four parallel lenses of one specialist maximize *coverage*, not *signal* - volume is not severity. Reviewing the proposed diff (not the applied one) is cheaper and lets you fold fixes in before the prompt file ever changes. When the user asks "what's a real problem?", that is the right instinct - answer it by separating real defects from reviewer inflation, not by treating all findings as equal.
- **Editing the currently-running command file trips the harness self-modification guard.** During `/execute` of the #125 plan, a batch-approved edit to `.claude/commands/execute.md` (the command that was actively running) was denied by the auto-mode classifier as self-modification, even though the identical edit shape to the other three command files (`explore.md`, `create-plan.md`, `pair-debug.md`) went through in the same batch. The classifier judged a bare "ok" after a status report too ambiguous to authorize editing the running command's own prompt. Fix: get an explicit, per-file approval for the running command's file ("yes, edit execute.md"), or make that one edit from a different session where it is not the active command. The normal prompt-file-approval flow covers the other command files; only the actively-executing one is treated as self-modification. (During #131 the same `/execute` run edited `execute.md` cleanly after an explicit AskUserQuestion approval, confirming the workaround.)
- **The self-modification guard also blocks adding a permission to `settings.local.json`, not just editing the running command.** During `/execute` of #131, an Edit to `.claude/settings.local.json` to add the `Bash(node .claude/scripts/session-init.js *)` allow rule was denied by the auto-mode classifier as self-modification of the permission machinery - even though the user had explicitly approved the surrounding prompt-file edits in the same run. The classifier treats the permission file as intent-resistant: a general "edit the files" approval does not authorize widening the allow-list, because that would let an agent grant itself capabilities. This is a sibling of the running-command guard above but a distinct surface (the permission file, not the active prompt). Fix: have the user add the permission line by hand, or grant an explicit Bash permission rule for that specific edit. Plan for it - a new script that needs its own `settings.local.json` permission entry cannot self-provision that entry during `/execute`; surface it as a user action item instead of silently failing. Related: "Permission approvals can land in the wrong settings file."
- **A prompt's user-facing message is not enforcement.** Discovered during the #123 research: `index.md`'s cost-confirmation message told the user chunk agents run on "Sonnet via general-purpose subagent" (line 42), but the dispatch instruction (line 50) specified no model, so chunks silently inherited the session model - Opus or Fable in practice. The claim sat unchallenged for versions because it looked like configuration. Rule: when a prompt asserts a runtime behavior (model choice, tool use, ordering), verify the instruction that executes it, not the message that describes it. The two can drift independently, and only the executing line is real. Fixed in #131: the Step 3 dispatch now pins the chunk agents to `model=sonnet`, so the message is true; the gloss "pin down, inherit up" was added so the rationale reads plainly.
- **Pin subagents freely; never switch the main-loop model mid-session.** From the #123 mechanism research, verified against current official docs: every model keeps its own prompt cache, so a main-loop model override (skill or command `model:` frontmatter) deep in a session forces an uncached re-read of the entire conversation history - once to switch, once to revert. That is one visibly slow turn each way, usually costing more than the cheaper model saves. Subagents build their own context from scratch anyway, so pinning them (agent frontmatter or the Agent-tool model parameter) has zero cache penalty. This is why /document stays on the session model while /index chunk agents get a Sonnet pin (#131). All 8 toolkits audited in #123 follow the same shape: route via subagent pins, never via main-loop switches.
- **A release needs one review of the whole range, not the sum of its per-issue reviews.** Eighty-two commits since the last whole-repo review point had each passed a per-issue review, and every one of those reviews was right about its own diff. Reviewing the range as five subsystems found the failures that no per-issue review can see: two individually correct #155 fixes that conflicted (`--no-abs` scrubbed screenshot paths before the embedder read them, so images vanished only on the published page), a rule naming a call site that did not exist (`/peer-review` in the HTML judgement table), a dedup rule fixed on the orchestrator path and missing on the direct path, a Windows installer three blocks behind the bash one, and docs describing a consent flow that the rule text had already changed. How to apply: before a release, run `/review` over `<last-review-point>..HEAD` grouped by subsystem and seeded with the per-issue findings as confirm-only, and look for the five range-only failure modes (conflicting fixes, changed-here-depended-on-there, interface drift, dead flags, silently changed defaults). Receipt: exploration pre-scan 18 receipted findings; the orchestrated range review 35 raw, 32 deduplicated, 22 survived the M2 audit, 10 refuted; `reports/findings-since-31d162c.md` sections 4a to 4g.
- **A version block describes what that version shipped; point at what changed since, never rewrite it.** The docs draft rewrote AGENT-SETUP's "What's new in v6.0.0" block to describe the post-6.0 no-ask publish as if 6.0.0 had shipped it, and the docs review rated that a Block: it was the exact "buried inside the 6.0 narrative" failure the owner's brief forbade, and it contradicted README's own 6.0.0 bullet. Worse, my own exploration finding F5 had called the correct 6.0.0 wording "stale pre-inversion text" because it sat in a block I read as current. How to apply: a "What's new in vX" block is history; when behavior changes later, add "(this has since changed: see the unreleased block above)" and put the current behavior in the unreleased block. Treat any finding that says a version block is "stale" with suspicion until you check which version the block describes. Receipt: docs review D1 (Block) and its fix in `ed36b2e`; F5 corrected in the findings report.
- **Numbers quoted in release notes mid-cycle go stale; fill counts in the last verify step.** README, AGENT-SETUP, and CHANGELOG quoted the guarantee suites at 93 (bash) and 115 (PowerShell) when the docs pass ran; the suites then grew three more times through review fixes to 129 and 148, and the range review flagged the stale numbers (R15). How to apply: write counts, sizes, and durations into release notes only in the final Verify step, from the suite output at final HEAD, and make that a checklist line. Receipt: R15; `ec8f3c2`.

## Mistakes to Avoid
<!-- Add patterns that caused problems so they don't repeat -->

- **Fill a plan's Outcomes by replacing the template placeholder, not inserting above it.** During `/execute` of #131, the filled-in `## Outcomes` content was added just above the plan template's own empty `## Outcomes` placeholder (the one carrying the "Fill in after execution" comment), leaving the finished plan with two Outcomes headings - one populated, one empty. The `/review` plan-compliance pass (R3) caught it: a trailing empty section makes a completed plan look abandoned, and any tool that reads the last matching heading would conclude no outcomes were written. Fix: when writing Outcomes at the end of `/execute`, edit the existing placeholder section in place (replace the comment with the real content) instead of adding a new heading. A quick `grep -c "^## Outcomes"` before finishing catches the duplicate.
- **Don't micro-tag individual bullets.** Tag sections, not lines. Wrapping every bullet in XML adds noise without helping parsing.
- **Watch for tool output artifacts in reviews.** The Read tool's output wrapper (`</output>`) can look like actual file content. Always verify with raw bytes before "fixing" something that might not be broken.
- **Review your own AI-generated code before shipping.** The initial worktree detection logic had a fundamental bug that would have broken every worktree feature. Running `/review-commands` and `/review-code` caught it. The review workflow exists for a reason - don't skip it even when the code "looks right."
- **Skill tool expansions can serve stale command versions.** Root cause: old command files in `~/.claude/commands/` (global/home directory) override the project's `.claude/commands/` files. In our case, 9 files were manually copied to the home directory in January before setup.sh existed, then never updated. When slash commands ran, the AI used the global copies instead of the current project versions - missing Staff Engineer Check, Finding IDs, and other updates. Fix: delete global copies (commands should only live in each project folder) and setup.sh now warns if it detects conflicting global files. See issue #52.

- **AI debates surface things standard reviews miss.** Running `/ask-gpt` and `/ask-gemini` alongside the 5 `/review-*` commands found insights none of the reviews caught: tone/task decoupling (shift questions but keep tone after scope narrowing) and the need for a vision-mode closing deliverable template. The debates push harder on behavioral edge cases because two models are actively challenging each other.
- **"Same command, two gears" vs "new command" decision pattern.** When debating whether to add a mode or create a separate command, the key question is: do they share enough structure? If the two behaviors use the same phases, question format, and guardrails (just different content), one command with modes. If they need different structure or workflow, separate commands. Applied this to `/explore` vision mode - both gears share Phase 1/Phase 2 structure, just different questions and tone.
- **CLI default-acceptance prompts don't fully translate to chat.** A prompt like `Scoping or vision? [scoping]` assumes the user can accept the bracketed default by hitting enter. In chat surfaces (Claude Code, Cursor), users always type *something* - the "press enter" branch is mostly dead. Prompts that use this convention need (a) synonym parsing for natural-language answers ("let's go vision", `v`, "big picture"), and (b) an explicit acknowledgement when input is ambiguous, rather than silently falling back to the default. Caught during the issue 88 review before it shipped.
- **When changing user-facing copy, grep for the same description elsewhere.** Updating README.md's `/explore` row drifted away from the toolkit.md description of the same command - same command, two stories. `/review-copy` flagged it. Cross-document consistency is a real review category, not just a nice-to-have. Refined in #137: "elsewhere" includes prompts embedded in script template strings, not just markdown. The issue #137 consistency pass grepped only `.md` files, so `ask-gpt.js` and `ask-gemini.js` kept telling the summarizer to "Mine the 3-round debate transcript" after the command files moved to "up to 3 rounds"; a fresh-context verifier sweeping all file types caught it. Grep by string, not by file extension.
- **Don't state a cited past lesson as if it happened this session.** During issue 130's wrap-up, suggesting a debate as the next step, the phrasing was "standard `/review` missed it - `/ask-gemini` caught it" - lifted from the issue-#98 lesson (where a debate caught the two-Summary bug). It read as if `/ask-gemini` had been run this session and had caught the `create-plan` double-prefix bug. Neither was true: no debate ran (the directory had zero debate artifacts), and the `create-plan` bug was caught by the Step 7 paired review subagents. The user challenged "when did you run Ask-Gemini? I never asked you to" and told me to check the directory. Lesson: keep the time frame explicit when citing history ("in issue #98, a debate caught..."), never phrase a cited precedent so it reads as a current-session action, and verify a tool actually ran before crediting it. Distinguish what you DID from what you're CITING. Sibling of "A prompt's user-facing message is not enforcement" - both are about not letting a plausible-sounding claim stand in for the verified fact.

### Skills migration decisions (issue #71)

- **Subagents do NOT auto-discover project skills.** The orchestrator must read skill files and pass content explicitly. You cannot assume a subagent will "just find" a skill in `.claude/skills/`.
- **Cross-directory file references in skills use `` !`cat ...` `` dynamic injection syntax, not `!include`.** This is how shared content gets pulled into skill prompts at runtime.
- **`@axe-core/playwright` is compatible with `playwright-core`** (peer dependency). No conflict with the library-only Playwright install the toolkit uses.
- **`user-invocable: false` works as documented.** It hides the skill from the slash command menu, but Claude can still invoke it programmatically. Useful for agent-only skills like `project-context`.
- **Shared files reduce duplication across review skills.** `.claude/skills/shared/` eliminated roughly 48 lines of duplicated content across 6 review skills.
- **GPT and Gemini peer review caught things standard reviews missed.** Zombie process risk, setup script legacy cleanup gap, missing documentation files, and an axe-core compatibility question all came from the debate rounds, not from `/review-*` commands.

### Doc audit + v5.0.0 release (issue #118)

- **Verify audit findings against file content before acting - subagent claims about file structure are not facts.** The audit subagent reported a "broken README anchor" (claimed `## What's new since v4.3.3` was not a markdown heading - it is, so the GitHub slug resolves fine) and a "missing /playground in AGENT-SETUP" (AGENT-SETUP has no command catalog, so there was nothing to add). Both were false positives. A 30-second `grep`/`sed` against the actual file would have caught each. Pattern: when a subagent reports a concrete, checkable claim ("X is not a heading", "Y is missing from Z"), confirm it on the real file before turning it into a plan task or an edit. The two genuine findings (the README /playground row and the three `html-outputs.md` contradictions) survived because I had verified them directly.
- **A major version bump on additive-only work needs explicit framing.** 4.6.0 -> 5.0.0 with no breaking change reads as an accident unless the release notes say "milestone, not a breaking change." State the intent in the first line of the CHANGELOG section and the GitHub release body.
- **Extending a running rollup beats adding a competing one.** The plan said add a "What's new since v4.6.0" section, but the toolkit already had a running `## What's new since v4.3.3` catch-up that chains every version. Adding a second would have forced repointing the README link and left two overlapping rollups. Extending the existing one kept the anchor valid and the narrative single.

### WSL opener + Windows installer parity (issues #119, #126)

- **Verify impact, not just existence, before scoping a fix.** The audit found `setup.ps1` never copies the `VERSION` file - a real asymmetry with `setup.sh`. But nothing downstream reads `$TARGET/VERSION` (the displayed version comes from a `sed`-stamped comment in `toolkit.md`; install-vs-upgrade detection keys off `toolkit.md` presence). Fixing it would have been change-for-nothing. The `generate-index.js` gap, by contrast, had a concrete failure (`/index` breaks with `MODULE_NOT_FOUND`). Confirm a gap actually *hurts* before adding it to scope - an absent file is not automatically a bug. (Extends the #118 "verify audit findings" lesson: verify the *impact*, not just the *claim*.)
- **A passing happy-path test is not enough - test edge cases, or let adversarial review hunt.** The new opener script was live-tested on WSL and passed (wslview absent -> PowerShell rung -> exit 0). But the test path had no apostrophe, so it missed a real bug: a Windows path like `C:\Users\O'Brien\...` breaks PowerShell's single-quoted `Start-Process` and silently no-ops - the exact failure the script was built to kill. `/review`'s adversarial code pass caught it; the happy-path test never would have. When a script handles variable/untrusted input (paths, names), test the awkward inputs or let a skeptical reviewer look for them.
- **Replacing LLM-run prose with a script removes non-determinism and shrinks the permission surface.** The opener was prose Claude executed step by step (fragile: a skipped fallback = silent no-op). Moving it into `open-artifact.sh` made the fallthrough deterministic (real exit codes) and collapsed six per-launcher permissions into one script permission, because the launchers became the script's child processes, not Claude's tool calls.
- **A containment check that compares path strings is not containment.** The new hosted-stamp code refused any `--local` path outside the repository by testing `abs.startsWith(root + sep)` on an unnormalized path. Two bypasses were reproduced in the review: an index row whose absolute path carried `..` after the root prefix, and a symlink inside `plans/` pointing at a file outside the repo; `--index-sync` would have rewritten either target. The first draft also had the opposite bug, refusing a worktree's own artifact because it compared against the main copy's root only, which the patch review caught before the code was even written. How to apply: normalize with `path.resolve`, then compare `fs.realpathSync` of both the candidate and the root (both sides, so a `/tmp` vs `/private/tmp` alias cannot false-negative), accept every root the file may legitimately live under (main copy and working copy), and restrict the operation to the file type it is for (`.html` only). Receipt: review C2 (Block) and R11/R17/R14/R18; fixes in `2a3e23e` and `3339f02`; `scripts/test-render-html.js` cases for `..`, symlink, worktree, and `.md` refusal.
- **A test must plant the state a failure actually leaves, not a convenient stand-in.** The interrupted-run scenario simulated a crash by deleting the manifest and three files. Under the atomic writer it was meant to prove, a real crash leaves the old manifest intact plus a partial `.toolkit-manifest.json.tmp`, so the scenario could not fail against a non-atomic writer at all. The same shape appeared twice more in one cycle: the worktree sync check asserted a stamp that `--index-add` had already written, and an error-name check grepped the whole log for a string the old bug also printed. How to apply: before trusting a new check, break the guard it protects and watch it fail; if it stays green, the fixture is not the failure state. Write the failure state down first ("what does the disk look like the moment after the crash?") and plant exactly that. Receipt: review C1 (Block), C9, C12; fixed in `2a3e23e`; every new check in the cycle carries a recorded fails-before/passes-after line.
- **A file that is both the maintainer's live config and the downstream seed leaks in both directions.** `.claude/settings.local.json` is this repo's working permission file and also the template the installers merge into every downstream project. Outward, maintainer-only grants ride along (16 of 39 entries added to one upgraded install were setup-script syntax checks, a WebFetch domain, an absolute-path Edit pattern). Inward, because the toolkit must track the file as the seed, its own `.gitignore` could never list it, so no downstream project ignored it either, and a fresh install's first `git add -A` staged a file full of machine paths that the pre-push tripwire then refused. How to apply: when one file serves two audiences, give the seed its own file or an explicit allowlist, and check what the seed carries into a fresh install before every release. Receipt: sweep S2 and W7 (open, owner decision), fresh-install walk W1 (fixed with an install-time ignore line in `7dc20b8`).

## Patterns That Work
<!-- Add approaches and conventions that proved effective -->

- **Tag vocabulary for prompts:** `<rules>` (must-follow), `<procedure>` (step-by-step), `<template>` (copy-paste schemas), `<output_format>` (expected output), `<conditions>` (if-then logic), `<guidelines>` (best practices), `<reference>` (lookup tables), `<phase>` (named stages), `<examples>` (good/bad demos).
- **Audit before converting.** Not every file needs XML. Short files, human-facing docs, and already-structured data are fine without it. Focus on files where the AI needs to distinguish content types.

### Rename-aware setup cleanup (issue #80)

- **`for i in "${!array[@]}"` is the idiomatic Bash way to iterate parallel indexed arrays.** First pass used `i=0; while [ $i -lt ${#arr[@]} ]; do ...; i=$((i+1)); done`. Both work and both are Bash 3.2 safe, but `${!array[@]}` expands to the index list, scopes the loop variable to the for-loop, and removes the manual counter. Reviewer caught it on the first pass. Use the for-form whenever you need indexes.
- **Scope parity gaps explicitly when fixing one of several.** While adding the rename block to setup.ps1, I noticed it was also missing the v3.4->v3.5 skills cleanup AND v4.0 plan migration that setup.sh has. Added only the rename block (issue #80 scope), surfaced the rest as a follow-up. Without explicit scoping, fixing "the obvious thing" tends to drag in adjacent fixes and turn a one-issue PR into a sprint.
- **A 🟩 on "ask the user about X" can mislead.** The plan-compliance reviewer flagged that marking the sub-task "ask whether to file a follow-up issue" as done was technically correct (I asked) but could read as "follow-up filed." For decision sub-tasks, either keep them 🟨 until acted on, or add a one-liner to Outcomes noting current status.

### browse.js hardening (issues #82 / #84 / #87)

- **Auto-start lifecycle code is hard to verify without a real dev server.** The fixes for #82 (`child.unref`, port snapshot, orphan-PID-don't-kill) all change `.claude/scripts/browse.js` process-management behavior (path was `scripts/browse.js` pre-v4.3), but exercising them requires `autoStart: true` plus simulated port conflicts and stale PIDs. Pipe-based smoke tests covered stdin parsing, browser launch, and `handleGoto` well; lifecycle changes shipped on code review only. Plan to do an end-to-end exercise on the next downstream `/review-browser` run that uses `autoStart: true`.
- **FS-probes for "is X installed" should fall through, not be authoritative.** First version of the Playwright cache-dir probe returned `BROWSER_NOT_FOUND` whenever the dir was missing - which broke Windows users (Playwright caches at `%LOCALAPPDATA%\ms-playwright`, not `~/.cache/ms-playwright`). Fix: only treat the probe as definitive when the dir EXISTS and is empty. Anything else falls through to the brittle-but-broader string match. The lesson generalizes: when you add a "smarter" check next to an existing fallback, gate the smart check on positive evidence, not on absence of evidence.
- **Lazy locators don't throw - validate at parse, not at construction.** `page.getByRole('buton')` does not throw; it returns a locator that finds nothing and times out 5s later. The original plan said "wrap getByRole in try/catch" - which would have caught nothing. The right fix was (a) validate the prefix syntax at parse time (`role:`, `role::Submit`, `role:button:` all throw immediately) and (b) thread the original target string into `ERR.TIMEOUT` so the eventual timeout names what the user tried. Pattern: when wrapping a deferred API, the wrapper has to either eagerly validate the input or carry context forward to the eventual error.

### HTML render pipeline (issues #120, #122, #127)

- **Prebuilt shell + data injection: the real #127 win is that a script has no "read-before-overwrite" constraint.** The slow / colliding HTML problem looked like a naming issue, but the deeper cost was Claude's Write tool refusing to overwrite a file it had not read this session, forcing a read-then-write of the stale file. Routing generation through a Node helper (which overwrites freely) eliminates that cycle entirely; the timestamp just prevents same-day name reuse. When a cost comes from a *tool constraint* rather than the logic, moving the work into a plain script can remove it outright.
- **Lift the gold artifact verbatim into a shared tokens file for zero visual regression - but make the mirror bidirectional.** Copying the existing review look's CSS into `tokens.css` guaranteed the new shells reproduced it exactly (the `/review` UX pass confirmed via real-Chromium DOM diff). The catch: `tokens.css` pointed at `html-look.md` but not vice-versa, so an edit to the documented source would silently not reach the rendered output. The `/review` plan pass flagged the one-directional mirror; both files now carry an "update both together" note, matching the setup.sh/ps1 parity pattern.
- **Emit JSON, let a script stamp the boilerplate - it is faster to generate and easier to verify.** Having commands produce a small JSON payload instead of hand-writing ~13KB of HTML cut generation time and made the output testable: each shell documents its own schema, renders from a fixture in isolation, and degrades gracefully on missing fields. Splitting "what to say" (JSON, model-generated) from "how it looks" (shell + tokens, static) is the same separation that makes the markdown-canonical / HTML-additive rule work.

### Plan HTML migration (issue #129)

- **Enforce invariants in code, not just comments - convention-only constraints erode as the codebase grows.** The "each injection slot must appear exactly once" rule in `render-html.js` was documented in shell header comments but only checked for presence (`indexOf !== -1`), not uniqueness (count === 1). The review caught the gap: a future shell author could accidentally duplicate a placeholder in a visible section, and the first-occurrence `.replace()` would inject the real data there, leaving the slot in the `<script>` tag unfilled - a broken page with no error signal. The fix is five lines. When a constraint is critical enough to call out in a warning comment, it is critical enough to enforce in code. The same logic applies anywhere shared infrastructure has a "MUST be exactly N" rule: add the assertion.
- **A top-level field list in a prompt reads as exhaustive - sub-field structure must be mentioned or it will be omitted.** When `create-plan.md` listed the top-level JSON fields (`title`, `subtitle`, ..., `steps`, `outcomes`), it implied `steps` was a flat value. The sub-fields within each step (`tag`, `meta`, `why`, `subtasks`) were documented only in the shell header comment, which the prompt said to "read for exact fields." Under context pressure or if the shell read is skipped, Claude produces steps with only `name` - no order pills, no dependency lines - a visibly degraded plan view with no error. Fix: after listing top-level fields, add one sentence naming the sub-fields of any complex object. This removes the false ceiling without duplicating the full schema. The general rule: if a field is an array of objects, name at least the key sub-fields in the prompt, not just in the referenced file.

### v5.2.0 release + doc audit (issue #128)

- **Self-enforce release-time conventions in the artifact or the checklist, not in memory.** Two maintenance conventions drifted silently across multiple releases: the AGENT-SETUP "keep only the last three release blocks inline" rule (established v4.5.1, five blocks inline by v5.1.0) and the CHANGELOG rollup's "lives at the top" placement (buried under four newer sections because the bump checklist said to add new sections at the "top of file"). Both rules existed only in past release notes and memory - nothing at release-prep time surfaced them, and release prep is exactly when attention is on the new content, not on old conventions. The #128 fix made both self-enforcing: a placement comment inside CHANGELOG.md right where the editor's cursor lands when adding a release section, and the three-block rule written into CONTRIBUTING's release checklist. Why it works: the rule now lives where the violation would happen, so following the normal process surfaces it - no memory required. How to apply: when an audit finds the same convention violated for the second time, do not just fix the instance - move the rule into the artifact it governs (a comment at the edit site) or the checklist that drives the edit. This is the process-and-docs analog of the #129 lesson "enforce invariants in code, not just comments."

### Host-agnostic gh/glab (issue #143)

- **Markdown table escaping leaks into shell commands when the file is inlined with `` !`cat` ``.** A jq filter was placed in an invocation-table cell, so its pipes had to be escaped as `\|` for the table to render. But `` !`cat` `` pastes the RAW file text into the prompt, and the shell does not strip a backslash inside single quotes, so jq would have received `\|` and errored. The table header made it worse by instructing "Use the whole row", which is a direct order to copy the cell verbatim. Confirmed with `od -c` rather than assumed. The near-miss was ugly: the consuming command happened to carry a correct unescaped copy inline, so the command file was accidentally safe while the shared reference every other caller reads was not. Rule: never put a shell command containing pipes inside a markdown table in a file that gets inlined. Move it to a fenced code block, where what the model reads is exactly what it should run. This generalizes past pipes - any character markdown needs escaped (backticks, underscores, angle brackets) is a candidate for the same trap.

- **A co-location rule is only as strong as its weakest call site.** The safety mechanism for host detection was co-location: put the detection in the same block as the command it guards, so skipping one means skipping the other. `document.md` implemented it correctly with an unconditional imperative. `explore.md` wrote "Detect the host before the first of those calls" - but BOTH of its call sites are conditional, so when the first never fires, the sentence is vacuously satisfied and the second call 135 lines later is unguarded. Same fix, same intent, two different strengths of instruction, and only one of them holds. How to apply: when the same safety mechanism is implemented across several files, trace each path independently rather than checking that the mechanism "is present" in each. Phrases like "before the first" and "if needed" are the tell: they make the guard conditional on something other than the thing being guarded.

- **Inlining a shared fragment AND repeating its content defeats the point of the fragment.** The change inlined `host-cli.md` into three commands and also wrote every command out verbatim underneath, so a single CLI flag change would have needed two or three edits instead of one - the exact cost the shared fragment was chosen to avoid. The drift was not hypothetical: the fragment itself predicted the trigger, warning that glab's JSON output flag has moved between versions. Fix was to reduce every call site to a pointer at the row by name ("run the 'Create issue' row for the detected host"). How to apply: after DRYing something into a shared file, grep the consumers for the content you just centralized. If it is still there, you have added a second copy rather than removed one. A bare identifier mention is fine; a full invocation with flags is duplication.

- **A permission you cannot self-provision may have an already-permitted equivalent.** Scoping flagged that host detection would need `Bash(git remote get-url *)` added to `settings.local.json` by hand, because the self-modification guard blocks Claude from adding permission entries during `/execute` (see the sibling lesson on that guard). Before accepting that as a user action item, it was worth asking whether a different command returns the same data: `git config --get remote.origin.url` produces the byte-identical string and was already covered by the existing `Bash(git config *)` rule, so the action item vanished. The rejected third option matters too: reading `.git/config` as a file needs no permission at all, but it breaks inside a worktree, where `.git` is a FILE pointing at the common dir rather than a directory - and this toolkit spends much of its time in worktrees. How to apply: when a plan produces a "user must add this permission" item, spend one minute looking for an already-allowed command that yields the same information, and check the worktree case before trusting any `.git/`-relative path.

### Human-in-the-loop map (issue #146)

- **A self-run consistency check passes while the scoped thing is missing entirely.** Writing the #146 decision map, the plan scoped a Step 2 subtask with three named items; two shipped as rules M2 and M3, the third (dispatch hygiene: verbatim bytes to audit agents) shipped nowhere, and the plan was marked done with Outcomes reading "No deviations". Every cross-check receipt passed honestly: the dash grep, the privacy grep, and the rule-ID consistency grep all came back clean - because an ID-consistency check can only validate rules that exist. A rule that never got an ID is invisible to it. The gap was caught by the /review plan-compliance specialist doing the one check the author's checklist did not: tracing each plan subtask's wording to a delivered artifact section. Two ironies made it a keeper: the missing rule was itself about review quality, and an external retrospective reviewed the same day had predicted exactly this failure class (a rules document violating its own standard, caught by the next review pass, not by the author). How to apply: after writing any spec-shaped artifact against a plan, verify scope-to-artifact traceability (every scoped item names the section that delivers it), not just the artifact's internal consistency. Internal checks prove what is there is coherent; only a plan-to-artifact trace proves nothing scoped is missing. This is the documentation analog of "A canary must assert the exact signal it claims to prove."

### Auto-by-default rewrite (issue #147)

- **A checked subtask means its wording shipped, not that the nearby diff did.** During #147, the plan's Step 5 subtask read "explore.md, create-plan.md, pair-debug.md: auto-run /index when the map is 10+ commits behind (M12)". Only explore.md carried the old warn-and-ask staleness text, so the edit landed there alone, the narrower work was rationalized as the task ("replace the warn-and-ask where present"), and the three-file subtask was checked done, with a Verify receipt ("every scoped file traces to a delivered edit") that was honestly overstated. The /review plan-compliance specialist caught it (finding R9) by re-reading the subtask's words against the diff: two named files had no delivered edit and no instruction to act on map.stale at all. This is the second occurrence of the #146 failure class ("A self-run consistency check passes while the scoped thing is missing entirely") - and this time the author RAN a traceability check and still passed it, because the check tested rule-to-fragment and file-to-edit, not subtask-wording-to-behavior. How to apply: when checking off a subtask that names N files or N behaviors, re-read the subtask's wording and demand a receipt per named item; "the text I expected to replace was absent" justifies a documented deviation, never a silent checkmark. Receipt: PLAN-issue-147.md Step 5 vs the git diff at review time; fixed post-review by wiring M12 into create-plan.md and pair-debug.md.
- **Call sites paraphrase a shared rule into different behaviors on day one.** The #147 rewrite created hitl-loop.md precisely to stop 17 files drifting, with call sites reduced to thin pointers citing rule IDs. The same day's /review still returned a Block (R1): M9's consequence was paraphrased three ways at four call sites - "stops the loop" (ask-gpt, ask-gemini), "page for approval instead of auto-applying" and continue (review-commands), "still stop the run" (execute.md) - because the fragment defined WHICH actions always ask but never the mechanics of what happens when one fires, so every call site improvised the missing half. A pointer only prevents drift for content the fragment actually contains. How to apply: when centralizing a rule, write its consequence into the rule itself (what happens next; does the process halt or continue) before wiring call sites; then audit call sites for consequence verbs (stop, halt, page, skip, continue) and replace improvisations with citations. Receipt: review finding R1 (Block) in artifacts/html/review-orchestrator-2026-08-28-234238.html; the fix defined page-and-continue plus single-page batching once in M9.

### M2 audit tiers (issue #148)

- **Adding a pipeline stage demands three sweeps: flow prose, data-lifecycle rules, and sibling-stage parity.** During #148, the M2 audit phase was inserted into review.md between dedup and the report, and the first live run of that audit reviewed its own diff and returned three surviving Warns - every one a missed sweep of the same file. (1) Flow prose: two sentences elsewhere in the file still described the pre-audit pipeline ("it simply has no subagents to dispatch" at the Phase 1.5 size gate; "from the deduped JSON findings (Phase 3)" in the Base Structure), each contradicting a new instruction lines away. (2) Data-lifecycle rules: the new required `receipt` field entered the JSONL contract, but the Phase 3 merge rule still enumerated only `specialist` and `fields`, leaving a merged finding's receipt undefined at a kill gate. (3) Sibling parity: Phase 2 had explicit subagent-failure handling; the new Phase 4 dispatched four subagents with none. M6 ("re-verify the claim, not the instance") names this class for fixes; this is the authoring-time version. How to apply: an edit that changes a pipeline's shape owes three sweeps of the edited file before shipping - every sentence describing the flow (grep for the old phase names and counts), every rule touching the changed data structure (merge, dedup, render), and every failure rule the sibling stages carry. Receipt: findings R2/R3/R5 in artifacts/html/review-orchestrator-2026-08-29-080956.html, fixed in commit 2514bb1.

### M11 tripwire hardening (issue #149)

- **A security control passes its own happy-path tests and still fails open - probe it with hostile inputs before trusting its exit code.** The #149 tripwire shipped with a Verify step that genuinely passed: a planted secret was caught, an added-then-removed secret was caught per-commit, a `.env` was caught in a subdirectory, the no-upstream fallback resolved. Every one of those tests fed the scanner the input it was built to catch. `/review` then returned a Block (R1, STANDS 3/3): git C-quotes any path containing a non-ASCII byte, so the patch header arrived as `+++ "b/..."`, the parser set `file = null`, and BOTH the secret scan and the never-push check silently skipped that file while the script exited 0 - the exit code that authorizes the push. Three independent skeptics reproduced it end to end, and one proved causation by setting `core.quotePath false` on the same scratch repo and watching the identical script catch both hits. The generalizable trap: tests written by the author of a control sample the space the author already imagined, and for a control the un-imagined space IS the threat model. How to apply: when the artifact is a gate, add a hostile-input pass before shipping - non-ASCII and quoted paths, content that mimics the format's own delimiters, two payloads where the code assumes one - and assert the gate FAILS CLOSED (reports what it could not read) rather than staying silent. Receipt: findings R1 (Block, 3/3), R2, R3 in artifacts/html/review-orchestrator-2026-08-29-092050.html; fixed in commit 0f9a78b, re-verified against the auditors' own reproductions.
- **Parse tool output with state and explicit decoding, never by prefix alone: content impersonates structure.** Two of the #149 findings were the same root cause in different clothes. In a unified diff, an added line whose text begins with `++ ` renders as `+++ ...`, indistinguishable by prefix from a `+++ b/path` file header - so a Haskell list concatenation at column 0 consumed the header slot and disabled the scan for the rest of that file (R2). Separately, git escapes special paths, so a prefix test for the literal `b/` failed on quoted ones (R1). Prefix matching treats a serialization format as if it were unambiguous; it never is. How to apply: parse with the state the format actually provides - here, the `@@` hunk header declares exactly how many added lines follow, so a line can only be structure when the parser is outside a hunk - and decode escaping explicitly rather than assuming the raw form. When a path or token still cannot be resolved, surface it as a hit instead of skipping it. Receipt: R1 and R2 in the same report; the fix added hunk-count tracking, `-c core.quotePath=false` on every git call, `-z` for the file list, and an unquote decoder whose failure is reported as unscannable.
- **Masking the match that triggered the report is not masking the line.** The tripwire masked secrets before printing them, because its own report lands in chat logs an LLM re-reads. But `line.replace(re, ...)` with a non-global regex rewrites one occurrence of one pattern, and the script emits a separate report line per matching pattern - so a line carrying an AWS key and an OpenAI key produced two report lines, each masking its own match and printing the sibling credential in full (R3, code and security independently). The redaction looked correct in every single-secret test. How to apply: redaction is a property of the whole output line, not of the match that caused it - apply every pattern globally to the line before printing, and test with two secrets on one line, plus the same secret twice. Receipt: R3 in artifacts/html/review-orchestrator-2026-08-29-092050.html; the fix masks through a global twin of every pattern, verified with a line carrying both an AWS and an OpenAI key.

### Stage chaining (M14)

- **A sweep's receipt is its grep patterns and their output, not the word "clean".** The stage-chaining cycle added rule M14 across nine files and closed with a three-sweep consistency check, exactly as the #148 lesson prescribes. The flow-prose sweep grepped four patterns ("Suggested next step", "Ready for", "when you are", "Natural next steps") and was reported as clean. None of the four matches "before suggesting", which survived at `explore.md:186` - twelve lines above the new chain check, in the flagship file of the whole change - and the clean result was then written into the plan's Outcomes as a passing receipt. Two more receipts in the same cycle failed the same way: a conjunction subtask ("cites M14 by ID AND no call site restates its mechanics") was checked green having verified only the first half, and a sibling-parity subtask substituted `git diff --name-only` for a semantics check it never ran, against a corpus it miscounted as 8 files when the real number is 24. The common shape: a pattern that misses is indistinguishable from a corpus that is genuinely clean, and an adjective ("clean", "confirmed") hides which one you got. This refines [[adding-a-pipeline-stage-demands-three-sweeps]] - running the three sweeps is necessary but not sufficient if their results are recorded as words rather than output. How to apply: write the command and paste its output; inspect every hit rather than counting them (one hit in this cycle's re-run turned out to be a pattern artifact, which counting alone would have misread); and when a subtask is a conjunction, produce one receipt per clause. Receipt: /review plan-specialist findings R8, R10, R11 in artifacts/html/review-orchestrator-2026-08-29-124944.html; corrected receipts now stored with their commands in plans/PLAN-stage-chaining.md Outcomes.

- **Fixing a drift finding means moving mechanics INTO the shared rule, not adding them at the call site.** Review finding R10 reported that the four M14 chaining call sites restated the rule's conditions in their own prose, and that `execute.md` had already diverged by adding a "plan at 100%" condition M14 did not contain. Fix round 1 removed the divergent condition, then resolved two sibling findings (R2, R3) by writing *new* mechanics into `explore.md`: a never-offered-scope-dial branch, and a vision gate keyed to "Remaining questions" where M14 said "Open questions". Neither was added to M14. The independent verifier failed R10 a second time, for precisely the defect R10 described, now caused by R10's own fix. Round 2 moved all four gate conditions into M14 (both field names, the sticky-mode dial condition, the never-offered branch, and the not-passing behavior) and reduced both call sites to a pointer plus a field-name mapping. The signal is directional and easy to check while editing: `explore.md` lost 7 lines. This is the fix-side companion to [[call-sites-paraphrase-a-shared-rule]], which names the problem; this names the direction out of it. How to apply: when a finding says a call site holds mechanics the shared rule lacks, the only correct direction is toward the rule. If your fix makes the call site longer, it is going the wrong way, however reasonable the added text reads. Receipt: verification round 1 "R10: NOT FIXED", round 2 "R10: FIXED"; `git diff 3ca51af` shows explore.md at -7 lines.

### Severity rubric + audit-aware direct runs (issues #150, #151)

- **A "nothing defines X" finding must first refute the generic rule that already covers X.** Both review passes this cycle authored a Block claiming a missing mechanism - the direct run's R2 ("the direct path has no check/expect authoring slot, so tier 1 kills everything or improvises") and the orchestrated run's R1 ("debate actions carry no runnable check, so the audit self-destructs on its own input") - and both died 3/3 in the three-vote for the same reason: a generic rule already covered the allegedly missing slot. The Receipt rule's "What you author here is the *check*" defines the mandatory `file:line` cite as the check, and M2 tier 1's judgment-finding clause supplies the matching expect ("the file read showing the cited pattern actually exists as described"). The specific slot really was absent; the capability gap was not, because the general rule filled it. Six independent skeptics across two runs converged on the identical refutation. How to apply: before authoring a missing-mechanism finding, grep for the general rule that would make the specific slot unnecessary, and refute THAT rule's applicability; proving only that the specific slot is absent proves nothing. Related: [[a-gate-must-be-countable-against-real-output]] - both failures came from reading a schema as exhaustive instead of reading the rules that interpret it. Receipt: "R2: REFUTED 3/3" in artifacts/html/review-commands-2026-08-29-140131.html and "R1: REFUTED 3/3" in artifacts/html/review-orchestrator-2026-08-29-174609.html, identical reasoning in all six ballots.

- **Centralizing a rule and hand-writing its call-site preamble in the same commit still drifts - quote the rule or say nothing.** Moving M2's audit mechanics into `hitl-loop.md` followed the exact direction the stage-chaining lesson prescribes ("mechanics INTO the shared rule"), and still reproduced the drift it exists to prevent: the ten skill call-site preambles were freshly written prose instead of quoted rule text, and they diverged from M2 inside the very commit that created them - M2 said "not a lighter one", all ten preambles said "not a cheaper one", alongside a second paraphrase of the runner sentence. The consistency reviewer caught it the same day and named it precisely: the copies "drifted at birth". The prior lessons ([[call-sites-paraphrase-a-shared-rule]], the moving-mechanics companion) cover paraphrase drift over time; this is drift at time zero - ANY fresh prose written next to an inlined rule is a second copy, however small and well-meant. The fix cut each call site to the one thing genuinely local to it (runner identity), and the ten preambles became one line each. How to apply: after centralizing a rule, a call site may state only what is local in the rule's own terms; every other word should be the rule's verbatim text or absent. Receipt: consistency finding R10 (grep receipt: 10 files matching "not a cheaper one" vs 1 matching "not a lighter one"), fixed in f3058b3.

- **A subagent lost to an account limit resumes as a narrowed retry scoped to what earlier passes did not cover.** The orchestrated run's commands specialist died mid-dispatch on the monthly API spend limit, after signaling "found a significant one in the debate commands" but before emitting any findings. Redispatching the original full-cycle prompt would have paid twice for ground the direct review had already covered in depth. The retry instead scoped to the single commit no reviewer had seen (f3058b3), stated what was already covered, and passed the dead agent's hint along as a place to look with an explicit "only report what YOU can prove" guard - a dead agent's hint is not a finding and must never be reported without its own receipt. The narrowed retry completed at a fraction of the original scope and delivered two receipted findings where the hint pointed; the audit then killed the Block 3/3, which is the pipeline working, not the retry failing. How to apply: when a dispatch dies partway on quota or limits, compute the remaining uncovered surface (what did prior passes actually cover?) and scope the retry to exactly that; carry hints forward as search targets, never as conclusions. Receipt: the spend-limit termination and the completed narrowed retry are recorded in this cycle's run; retry findings and their audit verdicts in artifacts/html/review-orchestrator-2026-08-29-174609.html.

### Subagent model pinning (issue #152)

- **Write the validation bar before the result, then honor it when the result is inconvenient.** The routing rule authored at the start of this cycle carried guardrail 3: "The pin ships only when the pinned run misses nothing real." The A/B then produced a genuinely mixed result - each arm found one real finding the other missed, 3 survivors each, and the pinned arm was 15% faster - which is exactly the shape that invites a post-hoc reading ("3-3 is fine, ship it"). But the finding the pinned arm missed was a real bug in shipped installer code, so the bar fired and the pin was revoked in the same cycle that proposed it. The value was in the ordering: the bar was written when the outcome was unknown, so honoring it cost nothing but consistency. Had the bar been written after seeing 3-3, any wording would have been reverse-engineered to fit. How to apply: when a change is justified by a hypothesis (faster, cheaper, better), write the countable pass/fail condition into the artifact BEFORE running the test, and treat a mixed result as failure unless the bar explicitly permitted it. A validation step that cannot fail is not validation. Related: [[a-gate-must-be-countable-against-real-output]]. Receipt: the revocation and its numbers are recorded in `.claude/skills/shared/model-routing.md` under "Tested and revoked"; the plan's Outcomes section carries the full comparison.

- **A missing finding is invisible to the audit; a wrong one is not.** The case for cheap finders rested on a real asymmetry: the M2 audit independently judges every finding, so a weak finder's junk dies before the user sees it. That reasoning is sound and it is also incomplete - it only covers findings that were reported. The audit has no input for a bug nobody raised, so false negatives pass through every tier untouched while false positives get three chances to die. The A/B made this concrete: the pinned arm's output looked perfectly healthy (6 findings, 3 survivors, no junk) and the gap was visible only by running the other arm on the identical diff and diffing the survivor sets. How to apply: when a quality argument leans on a downstream filter, ask what the filter cannot see. Filters remove; they never add. Any change that might reduce recall needs a comparison against a stronger baseline, not just a clean-looking output. Receipt: arm A produced 6 findings and never surfaced the `failglob` bug that arm B's receipt proved real; both arms' survivor sets are in the plan's Outcomes.

- **`failglob` beats `nullglob`, so a nullglob guard does not stop an empty-directory abort.** `setup.sh` sets `shopt -s failglob` globally, and four glob loops wrapped themselves in `shopt -s nullglob` believing that made an empty directory yield zero iterations. Bash resolves the conflict in failglob's favor: an unmatched glob still aborts with "no match", and under `set -e` that kills the installer before it prints anything useful. Two code comments asserted the false safety property in writing, which is what would have stopped a maintainer from finding it. The correct pattern is `shopt -u failglob; shopt -s nullglob` around the loop and the inverse afterward. Note the belt-and-braces `[ -f "$src" ] || continue` inside those loops never helped either - failglob aborts before the loop body runs. How to apply: when two shell options interact, test the interaction rather than reasoning about either one alone; a one-line `bash -c` repro settles it in seconds. Receipt: `bash -c 'shopt -s failglob nullglob; for f in /nonexistent/*.md; do :; done; echo NO-ABORT'` prints "no match" and exits 1 without printing NO-ABORT; fixed across all eight loop sites in 03ae0f3 and 18b2620, verified by a fresh installer run at both commits (49/49 installer guarantees passing).

- **Restricting an agent's tools is a behavior change, not a safety annotation - check what its callers actually need to run.** Adding `tools: Read, Grep, Glob` to the finder agent looked like pure hardening: it made a description that claimed "never edits files" actually true. It also silently broke two of the eight specialists dispatched through that agent, because Browser QA drives `browse.js` and Dependency Security runs `npm audit` and `gh api` - both need Bash, and neither could execute a single step of its criteria without it. The fix was not to revert but to grant Bash while withholding Edit, Write, and NotebookEdit, and to reword the claim from "never edits files" (a runtime guarantee the config cannot make, since Bash can write) to "declares no file-editing tools" (a statement about the frontmatter that is literally true). How to apply: before narrowing an agent's tool list, enumerate every caller that dispatches through it and check each one's actual commands; then make the prose claim exactly as strong as the config, not one word stronger. Related: [[a-prompts-user-facing-message-is-not-enforcement]] - the same class, one file over. Receipt: verifier verdict "NOT FIXED" on the first attempt naming both broken specialists, then FIXED after 18b2620 with the specialists' own SKILL.md tool requirements checked against the granted list.

### Second-viewport publishing (issue #154)

- **Check the permission allow-list before designing a mechanism out of shell commands.** The approved plan specified the artifact index as `echo '<json>' >> artifacts/html/index.jsonl` with a `grep`/`tail` lookup, and an ISO timestamp from `date`. None of `date`, general `grep`, or `tail` are in `.claude/settings.local.json`, so every one of those would have prompted, and a new helper script would have needed its own permission entry - which, per the #131 lesson, cannot be self-provisioned during `/execute` and becomes a manual step for the user. `Bash(node .claude/scripts/render-html.js *)` was already granted and the script is already copied by both installers, so moving the append and the lookup inside it as `--index-add` / `--index-url` shipped the feature with zero setup and zero installer parity work. Rule: before writing a plan step as a shell one-liner, grep the allow-list for the commands it needs. The cheapest place for new behavior is usually a script that is already permitted and already propagated, not the shell.

- **`<title>` is RCDATA, so escaping markup inside it changes nothing visible except entities.** The code reviewer flagged that HTML-escaping the payload title mangles the `topic` field, which the explore and debate shells document as accepting HTML, and I agreed out loud that I had introduced a real defect. The skeptic checked the actual parsing rules and refuted it: `<title>` is an RCDATA element, so `<code>` inside it is literal text whether or not it is escaped, and the page name renders identically either way. The only real difference is that an unescaped `&middot;` decodes to `·` while the escaped form shows the entity, and escaping additionally prevents a `</title>` in a payload from breaking out of the element. Net: the escaping is protective and the finding was wrong. Rule: when a review flags an escaping or encoding bug, check the parsing context (RCDATA, RAWTEXT, normal, attribute) before agreeing - the same escape is required in one context and inert in another, and conceding a defect you did not introduce is as costly as missing one.

- **A capability-shaped gate can be the honest option for a toolkit shipped to installs you do not control.** Two specialists independently called it a Block that the publish rule names no tool, only "a tool for publishing a file to a hosted artifact page is present in this session's tool list", citing this repo's own lesson that a gate must be one objectively-checkable condition. All three tier-3 voters refuted it, unanimously: a model can genuinely inspect its own tool list, so the condition IS checkable at runtime, and a toolkit installed into projects whose tool sets it does not control cannot hardcode a name it does not know. The worst realistic outcome was an additive feature silently no-opping while the local write and open still succeeded. Rule: "name the exact thing" is the right default for a gate, but it is a means to countability, not the definition of it. When the thing genuinely cannot be named at authoring time, a capability check the model can actually evaluate is not the same defect as a vibe, and severity should follow what breaks rather than which lesson the wording resembles.

### Viewport inversion + dark mode (issues #155, #156)

- **Mutation-testing a group of assertions is not mutation-testing each assertion.** After writing the `render-html.js` suite I ran a mutation pass: disable the absPath strip, disable image embedding, revert the index resolution, revert one shell's plain-text branch. All four were caught, so the suite was declared real. The review then found that two individual checks inside those groups could not fail under any circumstances: "never builds an editor link from relPath" evaluated `!a || !b` where both regexes matched no shell (they were written against a code shape that does not exist), and the no-repo fallback check was disjoined with `out.length > 0`, true for any successful run. Four mutations proved four groups were wired up; they said nothing about the individual assertions inside them, and the two dead ones happened to sit beside live ones that absorbed every mutation. How to apply: mutate against each assertion, not each feature. If you cannot name the specific line whose breakage a given check catches, that check has not been verified. Receipt: findings R9 and R22 in the #155 review; the second pass mutation-tests five behaviors individually and each fails the assertion that names it.

- **Tokenising the shared layer does not tokenise its consumers.** Dark mode was added to `tokens.css`, every token got a light and dark value, the mirror in `html-look.md` was updated, and a rendered page carried the `prefers-color-scheme` block, so it looked done. Seventeen hardcoded colors remained in the shells' own `<style>` blocks, which `tokens.css` does not govern - its header even says so. A hex literal survives a theme switch unchanged, and two of them set a background with no paired text color, rendering text at 1.05:1: white on white, in `explore-shell`'s recommended card and `docview-shell`'s zebra rows. A third was a live regression, `audit-shell`'s hand-cloned badge pill keeping `color:#fff` over a fill that lightens in dark mode. How to apply: after theming a shared file, grep every consumer for raw hex and treat each hit as unconverted until proven decorative. The consumers are where the theme actually fails. Receipt: findings R4, R5, R18, R26; `grep -rnE '#(eef2ff|f8faff|fafafa|...)' shells/*.html` returned 12 lines after the "complete" dark-mode commit and 0 after the fix.

- **A prose sweep needs the wordings that actually occur, not the one you remember writing.** Step 2 swept for copies of the "GitLab column has never been executed" caveat using `never been run` and `has not been executed`, showed the grep output as its receipt, and reported clean. The live copies in `README.md` and `AGENT-SETUP.md` read "has **never** been executed" and matched neither pattern. The worse of the two told an AI agent to warn the user at every fresh install that a now-tested path is untested. This refines [[a-sweeps-receipt-is-its-grep-patterns]]: showing the output is necessary and was done; the gap was that the patterns were invented from the phrasing being replaced rather than from the phrasings that exist. How to apply: grep for the shortest distinctive stem (`executed`, not `has never been executed`), then filter by eye. A sweep is cheap; a missed instance is a false statement shipped. Receipt: finding R2; `grep -rn "never been executed"` matched two files the sweep had declared clean.

- **A measurable claim in a commit message is a claim until you measure it.** The dark-mode commit asserted "Every dark pairing clears AA (~7.5:1 red and blue, ~11:1 amber)". Recomputed: red is 6.40:1, not 7.5:1, and the `audit-shell` veto badge was at 2.56:1, well under the floor. Both numbers came from reasoning about which tone should work rather than running the formula. The same overstatement was copied into `tokens.css` and `html-look.md`, so the file that declares itself the source of truth for contrast carried a wrong checkable number. How to apply: any ratio, count, or percentage stated in a commit message, a comment, or a doc is a receipt under M8 and needs the computation that produced it. Six lines of Python is cheaper than a reviewer discovering the number is decorative. Receipt: findings R18 and R27; the fix computes every text-on-surface pairing in both themes and prints PASS/FAIL per pairing.

- **A pipeline's exit status is the last command's, so `grep | head` always succeeds.** A pre-commit check for em dashes was written as `if git diff | grep -P '[em-dash]' | head -3; then echo FOUND`. `head` exits 0 whether or not `grep` matched anything, so the check reported a violation on a clean tree. Harmless here because it fired in the safe direction, but the identical shape fails silently when the guard is `if ! ...`. This is the same class as the two tautological test assertions found in the same cycle: three checks in one session that could not report what they claimed to report. How to apply: never put a filter after the command whose exit status you are testing. Use `grep -q ... && echo FOUND`, or capture into a variable and test that. Receipt: the check reported FOUND while a per-file `grep -c` returned 0 on all 19 changed files.

- **"Falls back" is not "degrades to nothing" - read what the fallback actually produces.** Exploration concluded that stripping `absPath` from a payload needed no shell change, because all five shells document that the file link "falls back to relPath when absPath is missing". They do. They fall back to building `vscode://file/<relPath>` - still a link, just a relative one that resolves nowhere for any viewer. The approved decision was plain text, so all five shells needed a branch after all, and the Verify step caught it rather than the review. The doc sentence was accurate; the inference drawn from it was not. How to apply: when a fallback justifies skipping work, read the fallback's code and name its actual output. "Falls back to X" describes the input it uses, not the shape of what it emits. Receipt: the #155 Verify step failed on "no vscode:// link" with the strip working correctly; five shells gained an `if (!file.absPath)` plain-text branch.

- **An audit with only pass and kill discards correct findings that carry the wrong label.** Two Block findings were refuted 3/3 in the #155 review. No skeptic argued either was false; all three wrote the same verdict in different words - real defect, wrong severity, Warn not Block. M2 has only `STANDS` and `REFUTED`, and `REFUTED` means logged and never fixed, so a correct finding exits on a severity technicality. One of the two was `AGENT-SETUP.md` instructing an AI agent to warn every install about a tested path; the other carried the fact that the whole issue had no CHANGELOG entry, which would have died with it. A human override was the only thing that saved both. How to apply: when a skeptic's reasoning says "real but over-severitied", that is a third verdict the format cannot express - read the reasoning, not just the verdict line. Filed as issue #158 to give M2 a downgrade path. Receipt: three independent ballots on R2 and R3, all refuting the Block claim while affirming the defect.

### Correction ledger (issue #157)

- **A filter whose misses are undetectable must reject only the certain non-matches, never guess the matches.** The capture pre-filter was built as the plan specified: a loose positive match on pushback words (`not right`, `actually`, `instead`, `undo`). Tested against a live session before committing, it caught 3 of 5 real interventions and missed two questions that challenged the work without containing a single pushback word ("should we keep it gitignored?", "how will downstream projects absorb this?"). A 40% miss rate on the one failure mode nothing downstream can detect, because the human only reviews rows that were surfaced and a row never surfaced is invisible forever. Rewritten as a NEGATIVE filter - remove machine text and bare acknowledgments, keep everything else, let a model judge the rest - it caught all 6. How to apply: when a false positive costs a few tokens and a false negative is permanent and silent, the asymmetry decides the shape. Do not enumerate what to keep; enumerate what is certainly not it. The pushback list survives as a non-gating `has_pushback_marker` hint, which is how the finding was proved: 3 of the 6 real interventions carry no marker at all. Receipt: `--candidates` on the authoring session returns 6, three flagged and three not; a regression test pins the exact shape that was missed.

- **Run your own receipt before you report it as confirmation.** A copy specialist raised a Block claiming the README omitted the consent gate, with the check `grep -ic 'confirm|say-so|approve|accept'`. I ran it, got 0, and reported that as confirming the finding. In basic regex `|` is a literal character, so that command searches for the string "confirm|say-so|approve|accept" and returns 0 for any input, including text containing every one of those words. All three Block voters caught it independently and refuted the finding. Re-run correctly with `-E`, the section does match, on "in your own words", which already conveys the user authors the row. How to apply: a receipt is only evidence if the command actually tests the claim. Before reporting a check's output as proof, run the inverse - feed the pattern something that should match - or the 0 you are quoting may be a syntax error rather than a result. This is the tier-1 discipline applied to the runner, not just to the specialists. Related: [[a-gate-must-be-countable-against-real-output]].

- **Two halves of one feature, written in one session, can each be right and still not meet.** `buildRollup` was written to emit bucket labels and counts, projecting rows through a privacy whitelist. `/error-analysis` was written to read the open codes out of the rollup and group them. Both were correct in isolation and both were written within an hour of each other, and the rollup never emitted an open code: it used the field only as a lookup key. The command could not perform its main step, and on a first run every bucket reads `(unlabeled)`, so the failure would have looked like thin data rather than a missing wire. Nothing in a single-author pass caught it; a commands reviewer found it and two of three Block voters reproduced it in their own sandboxes. How to apply: when one artifact produces and another consumes, run the actual pipe end to end before calling either done. Reading both files is not the same as running one into the other. Receipt: seeding a ledger with a unique open-code string and running `--show-rollup` returned it 0 times.

- **Harden every field on a whitelist, or the whitelist is not a boundary.** The ledger's privacy design rests on `shareable()`, a projection that makes reading a private field into a rollup structurally inexpressible. Every field in the row was derived by the script or truncated on write - except `at`, which read `at: r.at || now`, taking whatever the caller supplied. `at` is on the whitelist and feeds the rollup window and every bucket's last-seen value, so it was a free-text channel straight through the projection that existed to prevent exactly that. A security reviewer found it; I had hardened eight fields and missed the ninth. How to apply: a projection guarantees nothing about fields whose contents it does not control. Every field inside a whitelist must be derived at the boundary or format-validated on write, and adding a field to one is the moment to check which. Receipt: `at` now passes through `isoOrNull()`, and a test asserts free text placed there never reaches the ledger.

- **A test whose fixture is rejected by two code paths cannot detect either one breaking.** The suite asserted that the pre-filter excludes tool results, using a fixture whose content array held a single `tool_result` block. The guard rejected it - and so did the code underneath, because filtering for text blocks yielded an empty string that the next line rejected anyway. Deleting the guard entirely left the test green. It reported PASS and bought confidence in a protection it never exercised, which is worse than having no test. Fixed by pairing a text block with the tool_result so the guard is the only thing that can reject the entry. How to apply: for any assertion protecting a specific line, delete that line and confirm the test fails. An assertion that cannot fail is documentation wearing a test's clothes. Related: [[write-the-validation-bar-before-the-result]].

- **When storage is append-only, validate the whole batch before writing any of it.** `--add` checked each row for a required field inside the append loop, so a batch whose second row was invalid left the first row permanently written and exited non-zero. The natural response to that error - fix the bad row, run the same array again - re-appends the row that already landed. Append-only storage has no rollback and nothing marked the partial batch, and the duplicate is indistinguishable afterwards from a genuine recurrence. In a feature whose entire output is a recurrence count, that is a wrong answer rather than an inconvenience. How to apply: all-or-nothing is cheap when validation is a separate pass and expensive to retrofit once history exists. Receipt: a two-row batch with an invalid second row now leaves the ledger byte-identical, asserted in the suite.
- **Every fix lands with a check that failed first; a fresh context re-verifies the judgment ones.** Across this cycle 19 review findings on the installer and stamp work, 11 findings from the range review, and 5 doc findings were each fixed by an agent told to add a check, run it against the unfixed code, record the failure, then fix and re-run; mechanical fixes were re-verified by the suites (render 45 to 188, ledger 46 to 59, bash installer 51 to 129, PowerShell 51 to 148) and judgment fixes (contrast numbers, wording, plan bookkeeping) by a fresh verifier that re-measured rather than re-read. Two verifier passes returned 0 NOT FIXED and their M6 sweeps found four more instances of fixed claims that the fixes had missed. How to apply: the fail-then-pass line is the receipt M8 asks for; require it in the fixer's output contract, and never let the fixer declare its own judgment fix verified. Receipt: `2a3e23e`, `3339f02`, `054380b`, `2f3e0c5`; verifier journals in the session's workflow transcripts.
