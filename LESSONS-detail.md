## What I Learned
<!-- Add entries after each session where you learned something new -->

- **XML tags in prompts are a real thing, not just hype.** All three major providers (Anthropic, OpenAI, Google) recommend XML for complex, multi-section prompts. The key insight: XML helps AI distinguish *what kind of content* a section is (rules vs templates vs examples), which markdown headers alone can't do.
- **Hybrid approach beats all-or-nothing.** Don't replace markdown with XML - use both. Markdown headers stay for human readability, XML wraps content blocks for AI parsing. Pattern: header outside the tag, content inside.
- **AI peer review recommendations often over-engineer.** When /ask-gpt and /ask-gemini reviewed the XML plan, they recommended namespaced tags (`tk_rules`), a formal schema file, testing rubrics, and a three-wave rollout. Most of that was unnecessary for 9 small files. Trust your gut when something feels like too much.
- **A worktree is just a folder, a branch is just a pointer.** They're independent. Deleting a worktree folder does not delete the branch, PR, or any commits. You can always re-create a worktree from the same branch. Think of it like closing a document window vs. deleting the file.
- **Worktree detection: `--git-dir` vs `--git-common-dir`.** To check if you're in a Git worktree, compare `git rev-parse --git-dir` with `git rev-parse --git-common-dir`. If they differ, you're in a worktree. The first attempt used `--show-toplevel` vs `--git-common-dir`, which compares a directory path to a `.git` path - they're never equal, so it always said "worktree." The review process caught this before it shipped.

- **Use deterministic scripts for structural data, not LLMs.** When generating a file tree index, the first instinct was to have Claude scan and describe every file. Both GPT and Gemini called this out: "using an LLM to generate a token-saving index burns more tokens than it saves." A 20-line Node script using `git ls-files` does the job in milliseconds with zero token cost. Reserve LLMs for judgment calls, not mechanical tasks.
  - **Update (v4.4.0, issue #97):** The lesson is correct about mid-session LLM scanning, but during v3.4 it was over-applied to cancel ALL LLM involvement in index generation, including the one-time upfront generation that issue #70 originally wanted. The result (v3.4 through v4.3.x) was a flat file tree that did not save tokens at all - a directory listing is essentially free for Claude. v4.4.0 brings back the original vision: one-time upfront generation via parallel subagents (Cartographer-style), amortized over many sessions. Refined rule: **do not have Claude scan files mid-session; do invest tokens once when generating a persistent map the project keeps and rereads.** A ~$1 generation cost pays back across 5-10 sessions via reduced file reads.
- **Version bumps touch more files than you think.** Six files track the toolkit version: VERSION, package.json, package-lock.json, .claude/rules/toolkit.md (stamp comment), CHANGELOG.md, and AGENT-SETUP.md (title + "What's new" block). Easy to miss one - v4.2.1 shipped with package.json, package-lock.json, and toolkit.md stale; v4.1 missed toolkit.md too. **Use `bash scripts/setup/bump-version.sh <ver>`** - it handles the 4 mechanical files and prints a checklist for the 2 prose files. An earlier version of this lesson claimed "no automated fix possible because the checklist would leak to downstream users" - that was wrong. `scripts/setup/` is maintainer-only; setup.sh's propagation allowlist (setup.sh:352-354) only copies the three runtime scripts, so anything else added to `scripts/setup/` stays in the toolkit repo. (Status as of v4.5.0: setup.sh now lives at `scripts/setup/setup.sh` and the propagation block has moved to ~lines 463-465; the allowlist behavior is unchanged.)
- **Never interpolate shell variables into inline `node -e` strings.** If `$TARGET` contains a single quote (e.g., `/home/user/it's-a-project`), it breaks the JS string literal and `2>/dev/null` silently swallows the error. Pass paths via environment variables instead: `TARGET_DIR="$TARGET" node -e "const dir = process.env.TARGET_DIR; ..."`. This avoids all quoting issues.
- **`settings.json` can get modified by research subagents.** During the index format research, a subagent fetching aider.chat added a WebFetch permission and additionalDirectories to `.claude/settings.json`. Always run `git diff` before committing to catch unintended changes from subagent side effects.
- **Permission approvals can land in the wrong settings file.** When Claude Code prompts for a new Bash permission and the user approves it, the entry can get appended to `.claude/settings.json` (shared/committed baseline) instead of `.claude/settings.local.json` (user-specific, where the project convention says real permissions live). Also captures literal argument values, so test-run entries like `Bash(bash scripts/setup/bump-version.sh not-a-version)` end up in the file. Mitigation: `git diff .claude/settings.json` after approving any new permission, and move the entry to `settings.local.json` with a broader glob (`Bash(bash scripts/setup/foo.sh *)`) if the script is meant to be allowed long-term.

- **"Do I understand it?" vs "Can I use it?" is the right split for review skills.** When adding `/review-copy`, the key insight was that clarity/orientation and usability/accessibility are genuinely different concerns. A page can be perfectly usable (good contrast, accessible forms) but still confuse a newcomer who doesn't know what they're looking at. Separate skills with a clear tie-break rule ("meaning/orientation = copy, interaction/accessibility = UX") prevents muddled feedback.
- **Run debates on plans, not just finished work.** Running `/ask-gpt` and `/ask-gemini` on the plan (before building) caught four refinements that would have required rework later: audience assumption wording, severity anchor calibration, auto-detection heuristics, and the need for a non-goals section. Cheaper to fix a plan than to rewrite a shipped skill.
- **Boundary annotations in few-shot examples teach thresholds, not just format.** Adding a meta-note like "this would be skipped if X, is a Suggest because Y" inside an illustrative finding turns a passive template into an active boundary lesson for the model. Applied this in `output-template.md` to teach the Skip-vs-Suggest line via one example with explicit threshold logic, rather than padding the file with 5 borderline examples (issue #98).
- **DRY refactors create duplication-of-the-other-kind bugs.** When `/review`'s hardcoded output format was replaced with `!cat` inlining of the shared template, the shared template's own Summary block ended up rendering on top of the orchestrator's own Summary block - two Summary blocks per report. Standard `/review-*` checks missed it; the `/ask-gemini` debate caught it. Lesson: when DRYing, audit both sides of the new connection for what each independently provides (issue #98).
- **Issue framing != actual problem.** Issue #98 was titled "/review prompt may force model to manufacture issues" - the user's hypothesis was biased phrasing. `/explore` (vision mode) revealed the real problem: thin explanations + low severity bar, not invented findings. Trust the explore step to reframe even concrete-sounding issues; the original framing is just one hypothesis (issue #98).
- **Diagnostic output to stderr when stdout is captured by another LLM.** When a script's stdout flows into a downstream LLM's context (debate transcripts, multi-step workflows, anything that reads the script's output and puts it in a future prompt), any informational print silently pollutes the downstream prompt. `/review` caught this on the v4.5.0 model-bump safety net (issue #100): the new `Using GPT model: gpt-5.5` line and the deprecation warning were `console.log`, so they would have ended up in `/tmp/ask-gpt-debate.md` that rounds 2 and 3 re-read. Fix: route diagnostic prints to `console.error`; reserve stdout for "the payload another tool expects to parse." Rule of thumb: stdout = data, stderr = chatter.
- **Reasoning models share their token budget between reasoning and output.** `max_completion_tokens` (OpenAI) and `maxOutputTokens` (Gemini) cap the SUM of reasoning/thinking tokens and visible output. A 4096-token cap on a long-context input can be entirely consumed by reasoning, leaving zero tokens for visible output - the API returns `finish_reason: length` with empty content, exit code 0, no error. OpenAI's docs recommend reserving at least 25,000 tokens for reasoning models; Gemini's SDK default is 8,192 (we were below that). v4.6.0's GPT and Gemini scripts default to 32,000 with env overrides (`GPT_MAX_TOKENS`, `GEMINI_MAX_TOKENS`) for users who want lower caps to limit cost. See issue #101.
- **Silent empty bodies need active detection, not just happy-path returns.** Before #101's fix, both scripts had `return typeof text === 'string' ? text.trim() : ''` - any failure mode that produced empty content (token cap hit, refusal, safety block, wrong model) silently returned `''` with exit code 0. Detection means actively inspecting `finish_reason` (OpenAI) / `finishReason` (Gemini), `refusal`, `safetyRatings`, and `usage.completion_tokens_details.reasoning_tokens` / `usageMetadata.thoughtsTokenCount`, then throwing a descriptive error naming the cause AND the fix (e.g., "Raise GPT_MAX_TOKENS or shorten the input"). Token counts in the error are essential - "finishReason: MAX_TOKENS, thoughts_tokens: 92, candidates_tokens: 4" tells the user thinking ate 96% of budget, way more actionable than "empty body."
- **Per-session temp file paths solve concurrent-tab collisions; session-ID recovery needs to handle the multi-tab case.** Hardcoded paths like `/tmp/ask-gpt-debate.md` collide when two Cursor tabs run `/ask-gpt` in the same project. Fix: each slash command invocation generates a session ID (`echo "$(date +%s)-$RANDOM"`) and embeds it in every temp file path. Belt-and-suspenders: (a) write `<!-- Session: <id> -->` as the first line of the debate file so the ID is recoverable from disk if context compression drops it, (b) add `warnIfSessionMismatch` to the Node script that detects mid-flow ID regeneration via filename suffix comparison, (c) recovery instructions in the slash command must warn against blindly picking the most recent file under concurrency - it might belong to a parallel tab. See issue #101.
- **Run /ask-gpt and /ask-gemini in parallel when the change is worth real scrutiny; convergence between independent reviewers is signal.** Running both debates against PR #104 (4-field debate-summary format) surfaced the same template-slicing concern from both sides: GPT flagged that the inlined shared template could leak `/review`-only sections into debate output; Gemini independently flagged that the heading-based slice marker was fragile. Neither reviewer saw the other's transcript - they reached the same fix (machine-readable `BEGIN/END` markers around just the reusable finding contract) from different starting concerns. When two independent debates converge on the same gap, treat it as load-bearing: it almost certainly is. Running one debate gives you a second opinion; running both gives you a triangulation. Doubles the API spend, but worth it for changes you'd hate to re-fix later. Caught while validating the unchecked "end-to-end summary test" item from PR #104's test plan.
- **Cross-platform mirrors can hide pre-existing gaps; audit before assuming a small change stays small.** Mirroring a one-line addition from `setup.sh` to `setup.ps1` for issue #113 (`html-look.md` propagation) surfaced that `setup.ps1` had never copied `.claude/skills/` at all - every SKILL.md and shared reference file was missing on Windows. The "small mirror" expanded into "small mirror + gap fix" once the two scripts were compared side by side. Lesson: before mirroring a change, grep the target script for the prerequisite logic (`grep -i skills setup.ps1` would have caught this instantly). Document the scope expansion in the plan's Outcomes section so reviewers can audit the choice to expand vs defer. Related: two more `setup.ps1` gaps surfaced during the same review (no `VERSION` copy, no `generate-index.js` copy) and were correctly left out of scope as follow-ups - one expansion is fine, two compounds risk.
- **Define a judgement gate once, in countable terms, consistent with its governing rule.** Issue #116's debate-HTML gate shipped described three ways: the rule file said "3+ Recommended Actions," the new shared template added "OR genuine disagreement," and the command heading said "when the debate had substance." `/review` (both the commands and plan specialists, independently) flagged two problems: the template diverged from the single-source-of-truth rule file, and "genuine disagreement" would nearly always fire because debates are *designed* to argue across 3 rounds - making a "judgement" gate effectively default-on. Lesson: a gate should be one objectively-checkable condition (a count, not a vibe), and it must say the same thing everywhere it appears. When the same gate is described in 2+ files, they are now a consistency surface that drifts. Fix was to collapse to the single countable trigger across all three places.
- **`gh pr list --state merged --limit 1` sorts by CREATION date, not merge date.** It can return a stale PR (an old PR created long ago but merged recently sorts above a newer one). Discovered during #116's `/document` cycle-summary first-run fallback ("window since the last merged PR"): the command returned PR #104 even though #113-#116 shipped later (those went direct to `main`, not via merged PRs). For "most recently merged," sort explicitly: `gh pr list --state merged --json number,mergedAt --jq 'sort_by(.mergedAt)|reverse|.[0]'`, or use `git log --merges`. The D3 fallback in `document.md` still uses the naive `--limit 1` form - worth tightening in a follow-up.
- **HTML output is useless if the user only gets a file link - it opens as source in the editor.** Issue #102's HTML feature generated files in `artifacts/html/` and handed the user a path. In Cursor/VS Code, clicking that path opens the HTML *source code*, not the rendered interactive page, so the user saw markup instead of the dashboard. Fix (R4): after writing any HTML artifact, the command runs the platform opener (`open` on macOS, `wslview`/`explorer.exe` on WSL, `xdg-open` on Linux) so the rendered page opens in a browser, and the opener permissions live in `settings.local.json` so it does not prompt. Rule: if you generate something meant to be *viewed*, open it for the user; do not assume a link behaves the way you expect in their environment.
- **A diff review of already-closed work still earns its keep.** After #113-#116 were implemented and closed across several sessions, running `/review` on the cumulative diff (`<last-release>..HEAD`) surfaced 14 findings, including two real gaps: the `artifacts/` scaffold was never propagated downstream by either setup script (a tracked README that existed upstream but never reached users - same class as the earlier setup.ps1 skills gap), and the browser-open friction above. "Done and closed" is not "reviewed." When a multi-issue feature lands across several sessions, review the combined diff once at the end - cross-cutting gaps (propagation, file-to-file consistency) only show up when you look at all the pieces together, not issue by issue.
- **Don't trust merged review severities without verifying the source lines.** Discovered while triaging the /review report for issue #117. The plan reviewer claimed `/audit-html`'s SKILL.md inlined `html-outputs.md` twice (lines 33 AND 134), framing the second inline as a copy-paste defect. The commands reviewer reviewed only line 33's over-broad inline. In synthesis I merged the two findings into one R1 (Block) and reported it to the user as "two-character fix at line 134." It was a hallucination: line 134 already correctly inlines `html-look.md` (the visual tokens, which is what the HTML Report Judgement section needs). A 30-second `grep -n "^!cat" SKILL.md` would have shown the actual inlines and prevented the false escalation. Rule when merging cross-specialist findings: if two specialists describe the same finding differently (especially when one claims a defect the other did not see), open the file and confirm the line state before keeping the higher severity. Cheap to verify; expensive to send the user chasing a non-bug.
- **Review proposed prompt edits before applying them, and triage the volume hard.** Issue #121 added a conditional test-step heuristic to `/create-plan`. Instead of applying the edits then reviewing, we ran `/review` (review-commands, 4 parallel lenses) against the *proposed* text while the working tree was still clean - a pre-application review. It surfaced 13 findings across all three severities, but only ~3 were real: one true defect (the Verify step depended on a deletable optional setup step, so deleting it dangled), one genuinely valuable for the non-technical owner (no plain-English "why" on auto-added steps), and one cheap on-intent line (a "when in doubt, skip" tiebreaker). The other ~10 were edge cases an intelligent model handles, things already covered by existing wording ("and/or, whichever fits"), or scope-widening into files the issue never named (`execute.md`, map-absent fallbacks). Lesson: four parallel lenses of one specialist maximize *coverage*, not *signal* - volume is not severity. Reviewing the proposed diff (not the applied one) is cheaper and lets you fold fixes in before the prompt file ever changes. When the user asks "what's a real problem?", that is the right instinct - answer it by separating real defects from reviewer inflation, not by treating all findings as equal.
- **Editing the currently-running command file trips the harness self-modification guard.** During `/execute` of the #125 plan, a batch-approved edit to `.claude/commands/execute.md` (the command that was actively running) was denied by the auto-mode classifier as self-modification, even though the identical edit shape to the other three command files (`explore.md`, `create-plan.md`, `pair-debug.md`) went through in the same batch. The classifier judged a bare "ok" after a status report too ambiguous to authorize editing the running command's own prompt. Fix: get an explicit, per-file approval for the running command's file ("yes, edit execute.md"), or make that one edit from a different session where it is not the active command. The normal prompt-file-approval flow covers the other command files; only the actively-executing one is treated as self-modification. (During #131 the same `/execute` run edited `execute.md` cleanly after an explicit AskUserQuestion approval, confirming the workaround.)
- **The self-modification guard also blocks adding a permission to `settings.local.json`, not just editing the running command.** During `/execute` of #131, an Edit to `.claude/settings.local.json` to add the `Bash(node .claude/scripts/session-init.js *)` allow rule was denied by the auto-mode classifier as self-modification of the permission machinery - even though the user had explicitly approved the surrounding prompt-file edits in the same run. The classifier treats the permission file as intent-resistant: a general "edit the files" approval does not authorize widening the allow-list, because that would let an agent grant itself capabilities. This is a sibling of the running-command guard above but a distinct surface (the permission file, not the active prompt). Fix: have the user add the permission line by hand, or grant an explicit Bash permission rule for that specific edit. Plan for it - a new script that needs its own `settings.local.json` permission entry cannot self-provision that entry during `/execute`; surface it as a user action item instead of silently failing. Related: "Permission approvals can land in the wrong settings file."
- **A prompt's user-facing message is not enforcement.** Discovered during the #123 research: `index.md`'s cost-confirmation message told the user chunk agents run on "Sonnet via general-purpose subagent" (line 42), but the dispatch instruction (line 50) specified no model, so chunks silently inherited the session model - Opus or Fable in practice. The claim sat unchallenged for versions because it looked like configuration. Rule: when a prompt asserts a runtime behavior (model choice, tool use, ordering), verify the instruction that executes it, not the message that describes it. The two can drift independently, and only the executing line is real. Fixed in #131: the Step 3 dispatch now pins the chunk agents to `model=sonnet`, so the message is true; the gloss "pin down, inherit up" was added so the rationale reads plainly.
- **Pin subagents freely; never switch the main-loop model mid-session.** From the #123 mechanism research, verified against current official docs: every model keeps its own prompt cache, so a main-loop model override (skill or command `model:` frontmatter) deep in a session forces an uncached re-read of the entire conversation history - once to switch, once to revert. That is one visibly slow turn each way, usually costing more than the cheaper model saves. Subagents build their own context from scratch anyway, so pinning them (agent frontmatter or the Agent-tool model parameter) has zero cache penalty. This is why /document stays on the session model while /index chunk agents get a Sonnet pin (#131). All 8 toolkits audited in #123 follow the same shape: route via subagent pins, never via main-loop switches.

## Mistakes to Avoid
<!-- Add patterns that caused problems so they don't repeat -->

- **Fill a plan's Outcomes by replacing the template placeholder, not inserting above it.** During `/execute` of #131, the filled-in `## Outcomes` content was added just above the plan template's own empty `## Outcomes` placeholder (the one carrying the "Fill in after execution" comment), leaving the finished plan with two Outcomes headings - one populated, one empty. The `/review` plan-compliance pass (R3) caught it: a trailing empty section makes a completed plan look abandoned, and any tool that reads the last matching heading would conclude no outcomes were written. Fix: when writing Outcomes at the end of `/execute`, edit the existing placeholder section in place (replace the comment with the real content) instead of adding a new heading. A quick `grep -c "^## Outcomes"` before finishing catches the duplicate.
- **Don't micro-tag individual bullets.** Tag sections, not lines. Wrapping every bullet in XML adds noise without helping parsing.
- **Watch for tool output artifacts in reviews.** The Read tool's output wrapper (`</output>`) can look like actual file content. Always verify with raw bytes before "fixing" something that might not be broken.
- **Review your own AI-generated code before shipping.** The initial worktree detection logic had a fundamental bug that would have broken every worktree feature. Running `/review-commands` and `/review-code` caught it. The review workflow exists for a reason - don't skip it even when the code "looks right."
- **Skill tool expansions can serve stale command versions.** Root cause: old command files in `~/.claude/commands/` (global/home directory) override the project's `.claude/commands/` files. In our case, 9 files were manually copied to the home directory in January before setup.sh existed, then never updated. When slash commands ran, the AI used the global copies instead of the current project versions - missing Staff Engineer Check, Finding IDs, and other updates. Fix: delete global copies (commands should only live in each project folder) and setup.sh now warns if it detects conflicting global files. See issue #52.

- **AI debates surface things standard reviews miss.** Running `/ask-gpt` and `/ask-gemini` alongside the 5 `/review-*` commands found insights none of the reviews caught: tone/task decoupling (shift questions but keep tone after scope narrowing) and the need for a vision-mode closing deliverable template. The debates push harder on behavioral edge cases because two models are actively challenging each other.
- **"Same command, two gears" vs "new command" decision pattern.** When debating whether to add a mode or create a separate command, the key question is: do they share enough structure? If the two behaviors use the same phases, question format, and guardrails (just different content), one command with modes. If they need different structure or workflow, separate commands. Applied this to `/explore` vision mode - both gears share Phase 1/Phase 2 structure, just different questions and tone.
- **CLI default-acceptance prompts don't fully translate to chat.** A prompt like `Scoping or vision? [scoping]` assumes the user can accept the bracketed default by hitting enter. In chat surfaces (Claude Code, Cursor), users always type *something* - the "press enter" branch is mostly dead. Prompts that use this convention need (a) synonym parsing for natural-language answers ("let's go vision", `v`, "big picture"), and (b) an explicit acknowledgement when input is ambiguous, rather than silently falling back to the default. Caught during the issue 88 review before it shipped.
- **When changing user-facing copy, grep for the same description elsewhere.** Updating README.md's `/explore` row drifted away from the toolkit.md description of the same command - same command, two stories. `/review-copy` flagged it. Cross-document consistency is a real review category, not just a nice-to-have.
- **Don't state a cited past lesson as if it happened this session.** During issue 130's wrap-up, suggesting a debate as the next step, the phrasing was "standard `/review` missed it - `/ask-gemini` caught it" - lifted from the issue-#98 lesson (where a debate caught the two-Summary bug). It read as if `/ask-gemini` had been run this session and had caught the `create-plan` double-prefix bug. Neither was true: no debate ran (the directory had zero debate artifacts), and the `create-plan` bug was caught by the Step 7 paired review subagents. The user challenged "when did you run Ask-Gemini? I never asked you to" and told me to check the directory. Lesson: keep the time frame explicit when citing history ("in issue #98, a debate caught..."), never phrase a cited precedent so it reads as a current-session action, and verify a tool actually ran before crediting it. Distinguish what you DID from what you're CITING. Sibling of "A prompt's user-facing message is not enforcement" - both are about not letting a plausible-sounding claim stand in for the verified fact.

### Skills migration decisions (issue #71)

- **Subagents do NOT auto-discover project skills.** The orchestrator must read skill files and pass content explicitly. You cannot assume a subagent will "just find" a skill in `.claude/skills/`.
- **Cross-directory file references in skills use `` !`cat ...` `` dynamic injection syntax, not `!include`.** This is how shared content gets pulled into skill prompts at runtime.
- **`@axe-core/playwright` is compatible with `playwright-core`** (peer dependency). No conflict with the library-only Playwright install the toolkit uses.
- **`user-invocable: false` works as documented.** It hides the skill from the slash command menu, but Claude can still invoke it programmatically. Useful for agent-only skills like `project-context`.
- **Shared files reduce duplication across review skills.** `.claude/skills/shared/` eliminated roughly 48 lines of duplicated content across 6 review skills.
- **GPT and Gemini peer review caught things standard reviews missed.** Zombie process risk, setup script legacy cleanup gap, missing documentation files, and an axe-core compatibility question all came from the debate rounds, not from `/review-*` commands.

### Doc audit + v5.0.0 release (issue #118)

- **Verify audit findings against file content before acting - subagent claims about file structure are not facts.** The audit subagent reported a "broken README anchor" (claimed `## What's new since v4.3.3` was not a markdown heading - it is, so the GitHub slug resolves fine) and a "missing /playground in AGENT-SETUP" (AGENT-SETUP has no command catalog, so there was nothing to add). Both were false positives. A 30-second `grep`/`sed` against the actual file would have caught each. Pattern: when a subagent reports a concrete, checkable claim ("X is not a heading", "Y is missing from Z"), confirm it on the real file before turning it into a plan task or an edit. The two genuine findings (the README /playground row and the three `html-outputs.md` contradictions) survived because I had verified them directly.
- **A major version bump on additive-only work needs explicit framing.** 4.6.0 -> 5.0.0 with no breaking change reads as an accident unless the release notes say "milestone, not a breaking change." State the intent in the first line of the CHANGELOG section and the GitHub release body.
- **Extending a running rollup beats adding a competing one.** The plan said add a "What's new since v4.6.0" section, but the toolkit already had a running `## What's new since v4.3.3` catch-up that chains every version. Adding a second would have forced repointing the README link and left two overlapping rollups. Extending the existing one kept the anchor valid and the narrative single.

### WSL opener + Windows installer parity (issues #119, #126)

- **Verify impact, not just existence, before scoping a fix.** The audit found `setup.ps1` never copies the `VERSION` file - a real asymmetry with `setup.sh`. But nothing downstream reads `$TARGET/VERSION` (the displayed version comes from a `sed`-stamped comment in `toolkit.md`; install-vs-upgrade detection keys off `toolkit.md` presence). Fixing it would have been change-for-nothing. The `generate-index.js` gap, by contrast, had a concrete failure (`/index` breaks with `MODULE_NOT_FOUND`). Confirm a gap actually *hurts* before adding it to scope - an absent file is not automatically a bug. (Extends the #118 "verify audit findings" lesson: verify the *impact*, not just the *claim*.)
- **A passing happy-path test is not enough - test edge cases, or let adversarial review hunt.** The new opener script was live-tested on WSL and passed (wslview absent -> PowerShell rung -> exit 0). But the test path had no apostrophe, so it missed a real bug: a Windows path like `C:\Users\O'Brien\...` breaks PowerShell's single-quoted `Start-Process` and silently no-ops - the exact failure the script was built to kill. `/review`'s adversarial code pass caught it; the happy-path test never would have. When a script handles variable/untrusted input (paths, names), test the awkward inputs or let a skeptical reviewer look for them.
- **Replacing LLM-run prose with a script removes non-determinism and shrinks the permission surface.** The opener was prose Claude executed step by step (fragile: a skipped fallback = silent no-op). Moving it into `open-artifact.sh` made the fallthrough deterministic (real exit codes) and collapsed six per-launcher permissions into one script permission, because the launchers became the script's child processes, not Claude's tool calls.

## Patterns That Work
<!-- Add approaches and conventions that proved effective -->

- **Tag vocabulary for prompts:** `<rules>` (must-follow), `<procedure>` (step-by-step), `<template>` (copy-paste schemas), `<output_format>` (expected output), `<conditions>` (if-then logic), `<guidelines>` (best practices), `<reference>` (lookup tables), `<phase>` (named stages), `<examples>` (good/bad demos).
- **Audit before converting.** Not every file needs XML. Short files, human-facing docs, and already-structured data are fine without it. Focus on files where the AI needs to distinguish content types.

### Rename-aware setup cleanup (issue #80)

- **`for i in "${!array[@]}"` is the idiomatic Bash way to iterate parallel indexed arrays.** First pass used `i=0; while [ $i -lt ${#arr[@]} ]; do ...; i=$((i+1)); done`. Both work and both are Bash 3.2 safe, but `${!array[@]}` expands to the index list, scopes the loop variable to the for-loop, and removes the manual counter. Reviewer caught it on the first pass. Use the for-form whenever you need indexes.
- **Scope parity gaps explicitly when fixing one of several.** While adding the rename block to setup.ps1, I noticed it was also missing the v3.4->v3.5 skills cleanup AND v4.0 plan migration that setup.sh has. Added only the rename block (issue #80 scope), surfaced the rest as a follow-up. Without explicit scoping, fixing "the obvious thing" tends to drag in adjacent fixes and turn a one-issue PR into a sprint.
- **A 🟩 on "ask the user about X" can mislead.** The plan-compliance reviewer flagged that marking the sub-task "ask whether to file a follow-up issue" as done was technically correct (I asked) but could read as "follow-up filed." For decision sub-tasks, either keep them 🟨 until acted on, or add a one-liner to Outcomes noting current status.

### browse.js hardening (issues #82 / #84 / #87)

- **Auto-start lifecycle code is hard to verify without a real dev server.** The fixes for #82 (`child.unref`, port snapshot, orphan-PID-don't-kill) all change `.claude/scripts/browse.js` process-management behavior (path was `scripts/browse.js` pre-v4.3), but exercising them requires `autoStart: true` plus simulated port conflicts and stale PIDs. Pipe-based smoke tests covered stdin parsing, browser launch, and `handleGoto` well; lifecycle changes shipped on code review only. Plan to do an end-to-end exercise on the next downstream `/review-browser` run that uses `autoStart: true`.
- **FS-probes for "is X installed" should fall through, not be authoritative.** First version of the Playwright cache-dir probe returned `BROWSER_NOT_FOUND` whenever the dir was missing - which broke Windows users (Playwright caches at `%LOCALAPPDATA%\ms-playwright`, not `~/.cache/ms-playwright`). Fix: only treat the probe as definitive when the dir EXISTS and is empty. Anything else falls through to the brittle-but-broader string match. The lesson generalizes: when you add a "smarter" check next to an existing fallback, gate the smart check on positive evidence, not on absence of evidence.
- **Lazy locators don't throw - validate at parse, not at construction.** `page.getByRole('buton')` does not throw; it returns a locator that finds nothing and times out 5s later. The original plan said "wrap getByRole in try/catch" - which would have caught nothing. The right fix was (a) validate the prefix syntax at parse time (`role:`, `role::Submit`, `role:button:` all throw immediately) and (b) thread the original target string into `ERR.TIMEOUT` so the eventual timeout names what the user tried. Pattern: when wrapping a deferred API, the wrapper has to either eagerly validate the input or carry context forward to the eventual error.

### HTML render pipeline (issues #120, #122, #127)

- **Prebuilt shell + data injection: the real #127 win is that a script has no "read-before-overwrite" constraint.** The slow / colliding HTML problem looked like a naming issue, but the deeper cost was Claude's Write tool refusing to overwrite a file it had not read this session, forcing a read-then-write of the stale file. Routing generation through a Node helper (which overwrites freely) eliminates that cycle entirely; the timestamp just prevents same-day name reuse. When a cost comes from a *tool constraint* rather than the logic, moving the work into a plain script can remove it outright.
- **Lift the gold artifact verbatim into a shared tokens file for zero visual regression - but make the mirror bidirectional.** Copying the existing review look's CSS into `tokens.css` guaranteed the new shells reproduced it exactly (the `/review` UX pass confirmed via real-Chromium DOM diff). The catch: `tokens.css` pointed at `html-look.md` but not vice-versa, so an edit to the documented source would silently not reach the rendered output. The `/review` plan pass flagged the one-directional mirror; both files now carry an "update both together" note, matching the setup.sh/ps1 parity pattern.
- **Emit JSON, let a script stamp the boilerplate - it is faster to generate and easier to verify.** Having commands produce a small JSON payload instead of hand-writing ~13KB of HTML cut generation time and made the output testable: each shell documents its own schema, renders from a fixture in isolation, and degrades gracefully on missing fields. Splitting "what to say" (JSON, model-generated) from "how it looks" (shell + tokens, static) is the same separation that makes the markdown-canonical / HTML-additive rule work.

### Plan HTML migration (issue #129)

- **Enforce invariants in code, not just comments - convention-only constraints erode as the codebase grows.** The "each injection slot must appear exactly once" rule in `render-html.js` was documented in shell header comments but only checked for presence (`indexOf !== -1`), not uniqueness (count === 1). The review caught the gap: a future shell author could accidentally duplicate a placeholder in a visible section, and the first-occurrence `.replace()` would inject the real data there, leaving the slot in the `<script>` tag unfilled - a broken page with no error signal. The fix is five lines. When a constraint is critical enough to call out in a warning comment, it is critical enough to enforce in code. The same logic applies anywhere shared infrastructure has a "MUST be exactly N" rule: add the assertion.
- **A top-level field list in a prompt reads as exhaustive - sub-field structure must be mentioned or it will be omitted.** When `create-plan.md` listed the top-level JSON fields (`title`, `subtitle`, ..., `steps`, `outcomes`), it implied `steps` was a flat value. The sub-fields within each step (`tag`, `meta`, `why`, `subtasks`) were documented only in the shell header comment, which the prompt said to "read for exact fields." Under context pressure or if the shell read is skipped, Claude produces steps with only `name` - no order pills, no dependency lines - a visibly degraded plan view with no error. Fix: after listing top-level fields, add one sentence naming the sub-fields of any complex object. This removes the false ceiling without duplicating the full schema. The general rule: if a field is an array of objects, name at least the key sub-fields in the prompt, not just in the referenced file.
