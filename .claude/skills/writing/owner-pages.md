# Pages and files written for the owner

**Who reads it.** The owner first, deciding whether to approve or act. The next stage or a later session second, which needs the exact detail. Examples: a plan, an exploration summary, a review summary, a cycle page.

**Order**
1. An exploration summary and a plan open with an "In plain words" block, five bold labels: The problem; The goal and how we will know; The cost; What is left out; What changes for you.
2. The stage's own layout follows, unchanged. The stage's template owns the layout; this file owns the words.
3. Exact detail comes last: file names, commands, hashes and codes belong in the proof, the receipt row or the step's file list.

**Rules**
- Write the block in everyday words: someone who never saw the work should understand what happens, what it costs and what is asked of them.
- The cost names money and time when either is spent, and says so when nothing is.
- "What changes for you" says what the owner will see, do or be asked.
- A review summary line keeps its shape: number, verdict, plain words, proof. The plain words say what changed for the reader, not which file moved.
- Give each thing one name and keep it for the whole page.
- No line in the block starts with a label a script reads, such as `**Models:**`, `**Mode:**` or `**Scope dial:**`.

**Example.** The before text is real, from an exploration summary in this toolkit; the topic is specific to it, and the shape is the rule.
- Before: "Two valid runs make a build measured. The scorer treats one miss in a single run as 'run again', so one run can never be scored; two is also what the plan gate asks for."
- After: "**The problem:** the review can get worse at catching bugs between releases, and nobody notices. **The goal and how we will know:** a release that changes the review waits until the review has been tested twice on the practice project; the release check prints a pass line naming the tests, or stops and names the command to run."
