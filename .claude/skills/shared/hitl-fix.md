# The Auto Loop: fixing (M3 to M8)

Rules M3 to M8 of the toolkit loop: how a fix is made, checked, committed and bounded. They continue `.claude/skills/shared/hitl-loop.md` (the overview, M1 and M2) and go on in `.claude/skills/shared/hitl-stages.md` (M9 to M17). The loop rules skill loads all three files. The after-report skill loads this one again with the steps a review takes after its report, because after a compression Claude Code keeps only the start of each loaded skill, and a small skill loaded late is kept whole.

## Auto-fix mechanics

- **M3. The fixer never verifies.** Trust order for verification signals: a runnable check first, a different model second, a fresh same-model context last. The agent or conversation that produced a fix never declares it verified. Which path each surviving finding takes is the runner's judgment; the mechanics of every path are the mode's. A mechanical finding (a test, build, or script exit code demonstrated it) is re-verified by re-running its own check, and the checks runner's pass is FIXED. A fix that keeps its receipt's matched text goes under `--judgment`; the mode catches only `match` file searches (`text_kept`). A judgment finding (quality, clarity, UX - nothing runnable proves it) is re-verified by fresh subagents per round, one per 7 findings, ceiling, the same shard rule as M2 tier 2 and for the same reason. The instruction each verifier follows, word for word: Read the diff of the fixes against each finding's own words. "FIXED" means the defect the finding named is gone in the code as it now stands, not that a change was made near it. Return exactly one line per ID - "RN: FIXED" or "RN: NOT FIXED" - plus a one-line receipt each. Anything new you notice goes in your reasoning line as a note for the runner, never as a verdict. A judgment finding whose truth is what a browser renders, on a surface that can be served, takes the mechanical path through a `browse.js` check written before the fix and re-run after it, named under `--browser`; without such a check it stays with the verifiers. A logic finding a test can show takes the check-first path (M17): a failing test before the fix, kept after it, or with no test runner a read-only check that fails before and passes after; with neither, the verifiers decide. After the fixes the runner runs `node .claude/scripts/merge-findings.js --verify <the folder holding findings.jsonl> --receipts reports/receipts/<run-stamp> --scope reports/receipts/<run-stamp>/scope.json --out reports/receipts/<run-stamp>` (M16), naming each survivor under `--mechanical`, `--judgment` or `--browser` by its path and leaving out any flag with no IDs, since the mode refuses an empty one. It writes the recheck rows, the verifier shards and the run's ledger from the bytes on disk and prints `next`, what consumes each file, in order; the runner's job is then to run what it prints, in order, and nothing else. The shards carry the diff since the point the review started from, read from `scope.json` (`uncommitted.baseline`, else `range.end`); a runner with no scope call saves one with `node .claude/scripts/session-init.js --scope --out reports/receipts/<run-stamp>/scope.json` before its first fix. Those verifiers are `fix-verifier` agents (`subagent_type=fix-verifier`): no edit tools, `effort: high`, session model, per the roster in `.claude/skills/shared/model-routing.md`; a verifier that could edit would be a fixer.
- **M4. Checkpoint commits.** Commit after each green logical unit; in a plan, a step is green when its after run passes (M17). The checkpoint is the undo button that makes auto-fix safe: a bad fix reverts surgically without dragging good work along. In the fix loop, record each checkpoint right after its commit with `node .claude/scripts/merge-findings.js --checkpoint --ledger reports/receipts/<run-stamp>/ledger.json` (M16): it writes HEAD into the run's ledger as the last green, with the IDs FIXED in their current round and a count of tracked changes still uncommitted, which should be zero and is flagged when it is not. A checkpoint commit carries only the fixes that read FIXED: an attempt that read NOT FIXED is undone in the tree before the commit, so the sha the ledger records is green and the next round starts from it.
- **M5. Bounded, then revert, then page.** Max 2 fix rounds per finding; the run's ledger counts them, and the mode refuses a third call for a finding (`rounds_exhausted`), writes nothing for any ID that call named, and names the last recorded green. The one call past that bound is the fresh verifier the mode itself prints when a rewritten check still fails, a filled-in check passes, or a search receipt's text survives the fix: it judges the same fix, so it spends no round and no third attempt opens. Still red after round 2: revert to that checkpoint (with none recorded, to the point the review started from: the scope's snapshot, else its pinned end), stop, and page with a 3-line summary: what the finding is in plain words and what happens if it ships as is, what failed, and what was tried; the other IDs in the refused call wait for the answer. Never a third attempt on the loop's own word, never silent continuation. The page names "try once more" as an answer: on the owner's yes, the runner fixes again and adds `--owner-try <ID>` to that finding's next `--verify` call, which opens round 3 once and marks it the owner's in the ledger, and its digest line reads `(round 3, the owner's choice)`. Red again: revert and page without that answer. A check that fails then passes on rerun (`run-checks.js --rerun-failures` marks it `flaky`) is logged as a finding for the digest, never silently reclassified as green. New findings discovered during re-verification get one follow-up generation: deduped, guarded, appended to the run's `findings.jsonl` with `"followup": true` so each takes the next free number and no ID moves, fixed, and re-verified once, named to the mode beside the round-2 IDs, since it counts rounds per finding and not per call. Anything surfacing after that lands in the digest as an open item for the next run - fix chains never grow unbounded.
- **M6. Re-verify the claim, not the instance.** A finding names one occurrence; what it reports is a claim that can have several. Before declaring a fix done, sweep the touched files for other instances of the same claim. A fix is new work and meets the same evidence bar as the finding that prompted it.
- **M7. Intent-reversal guard.** Before applying a fix, check whether it would restore or undo something the git history, the diff, or the reviewed range's commit messages show was deliberately changed or removed. If so, page instead of applying, even when the finding is technically correct.
- **M8. Receipts, not claims.** Digests and documentation state what ran and show the evidence: the command and its output, the count delta, the diff stat. "All N fixed" without receipts is the failure mode, not the report. A doubt closed as "deliberate" carries a pointer to where the human actually decided it; otherwise it stays open.
